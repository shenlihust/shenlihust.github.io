# 写作与维护

## 本地预览

使用 Ruby 3.4 与 Bundler：

```sh
bundle install
bundle exec jekyll serve --host 127.0.0.1
```

打开 http://127.0.0.1:4000 。修改 `_config.yml` 后需要重新启动预览。

macOS 如果默认 Ruby 版本过旧，可在当前终端执行：

```sh
export PATH="/opt/homebrew/opt/ruby@3.4/bin:$PATH"
```

## 发布文章

在 `_posts` 新建 `YYYY-MM-DD-english-slug.md`：

```yaml
---
title: "文章标题"
description: "一句话概括文章解决的问题"
date: 2026-10-20 10:00:00 +0800
categories: [原理与架构]
tags: [数据库, 索引]
toc: true
mermaid: true
---
```

正文使用 Markdown。分类建议使用 `原理与架构`、`源码解读`、`工程实践`、`实验记录`；标签按具体技术填写，例如 `Python`、`数据库`、`Kubernetes`、`Agent`。不限定技术领域，分类和标签页会根据已发布文章自动生成。`categories` 中的多个值表示层级，而非平行栏目。

草稿放到 `_drafts/slug.md`，使用 `bundle exec jekyll serve --drafts` 预览；默认构建不会发布草稿。文章图片建议放在 `assets/img/posts/文章标识/`。

## 技术文章解析专栏

本站主要记录 AI 技术学习与开源项目分析。文章页面不显示作者栏，网站版权署名使用 `shenli`。不把未进行的实践或实验写成亲身经历。

「技术文章解析」作为普通文章分类，统一从侧边栏「分类」页进入，不单独增加专栏导航。先在本地完成写作与校对，再按发布流程发布；新增文件不等于提交或部署。

解析文章 front matter 示例：

```yaml
---
title: "中文标题"
description: "一句话介绍文章主题"
categories: [技术文章解析]
tags: [Anthropic, Agent, 评估]
toc: true
---
```

### 来源与定位

正文开头注明原文标题、原作者、原文链接与发布日期。用自己的案例和推导展开分析，明确区分原文观点、个人判断、教学示例和实测结果；只引用必要的少量原文，在相关论述附近标明来源。

机构标签按所解析文章的来源填写，例如 `Anthropic`，并搭配具体技术标签。标签用于聚合本站相关文章，原文链接单独保留。不要仅因正文提及某家公司，就自动添加它的机构标签。

### 写作流程与关键内容覆盖

1. **通读并列出核对清单。** 覆盖原文的问题背景、关键术语、方法分类、指标定义、实施步骤、适用条件和限制，同时清点正文图表及其讲解作用。
2. **确定解析主线。** 用一个具体问题或原创工程案例串联方法，解释这些方法解决什么问题、怎样应用、可能在哪里失效。可以重新组织顺序，不机械逐段翻译。
3. **展开关键差异。** 原文区分多种系统、Agent 或方法时，分别说明评价对象、所需证据、检查方式和常见误判，不能只列名称。原文给出实施路线时，核对步骤编号、数量与依赖关系，并对应到具体行动或交付物。
4. **核实技术细节。** 对公式说明假设、变量与统计口径；对示例标明是否实际运行。涉及论文、基准或工具时，优先核对一手资料，不把历史成绩写成当前事实。
5. **回到原文逐项复核。** 检查是否漏掉关键观点、前提、例外与图表表达的信息。对刻意未展开的客户故事、完整配置或工具介绍，说明范围并保留阅读入口，不把“采用自己的结构”当作遗漏关键内容的理由。

较长文章可在 `docs/文章标识-review.md` 保留核对记录，包括主要遗漏及补充、图解覆盖关系、来源和验证结果。示例见 [Agent 评估解析核对记录](anthropic-agent-evals-review.md)。

### 推荐正文结构

- 从具体问题切入，给出核心判断与原文信息。
- 解释理解后续内容所必需的概念与关系。
- 用原创案例、代码或数据展开关键方法，分清方法之间的差异。
- 给出实施步骤、验收证据、常见失败与适用边界。
- 保留原文及补充一手资料入口，说明本文未展开的范围。

根据主题调整结构，避免在每个章节反复复述同一观点。读者应既能理解原文的关键方法，也能看出解析增加了哪些推导、判断和实践细节。

### 原创中文图解

按内容选用 `excalidraw-diagram` 或 `imagegen`：流程、关系、结构和可编辑技术图优先使用 Excalidraw；需要插画或位图视觉时使用 imagegen。配图应帮助解释关系、差异或因果，不只是把段落放进方框。

原文有多张图时，逐张核对它们承担的讲解作用，再决定合并、拆分或新增原创图解。图数不必相同，但不能只放一张总览图而遗漏其他图承载的关键知识点；也不要为了凑数量添加装饰图。

图片放入 `assets/img/posts/文章标识/`，可编辑的 Excalidraw 源文件放入 `assets/diagrams/文章标识/`。每张图提供中文替代文本、图注；源文件保留在仓库中，正文和文末不再添加下载说明或链接。图注说明原创、示例或实测性质，不把假设数据写成模型成绩。

Excalidraw 必须经过渲染、查看、修正的循环，检查文字、箭头、对齐、遮挡与阅读尺寸；生成图也要检查中文文字和技术含义。最终图片必须存入博客目录，不能依赖生成工具的临时位置。

### 本地验收与发布边界

- 构建站点并检查站内链接、目录锚点、图片及仓库中的配图源文件。
- 在浏览器查看正文图表，检查桌面和手机阅读效果；未实际检查的项目不声称已验证。
- 点击专栏与机构标签，确认列表收录正确，并能返回对应文章。
- 可执行代码进行与风险相称的验证；没有运行的示例明确标注。
- 默认完成本地编辑与预览。未经明确要求，不提交、推送或部署；提交时只包含用户授权的范围。

## GitHub Pages

目标仓库：`shenlihust/shenlihust.github.io`。

创建仓库并上传本站源码后，在 Settings → Pages → Build and deployment 中选择 GitHub Actions。仓库已附带官方构建部署工作流，推送到 `main` 会自动构建和部署。

提交本地生成的 `Gemfile.lock` 前，执行 `bundle lock --add-platform x86_64-linux`，确保 Linux 构建环境可用。

## 修改样式

- 名称、简介、头像、主题模式：`_config.yml`。
- 关于页：`_tabs/about.md`。
- 侧边栏链接：`_data/contact.yml`。
- 更深入的样式调整：按 Chirpy 官方说明覆盖 `assets/css/jekyll-theme-chirpy.scss`，保留主题导入，再追加自定义样式。

优先保留主题默认模板，只覆盖确有需要的文件，减少后续升级成本。

参考：https://chirpy.cotes.page/posts/getting-started/
