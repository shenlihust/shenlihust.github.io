给一个已有产品增加团队权限管理，需要修改数据库、后端接口、前端页面，还要补上越权访问测试。让一个 Agent 从头做到尾，它可能在处理页面细节时忘掉接口约束；让五个 Agent 一起做，又可能得到五份各自合理、合起来无法运行的结果。

问题出在哪里？前端采用了 `admin`，后端使用 `owner`；测试验证的是旧接口；审查者收到“已经实现权限检查”的总结，却没有看到真正执行检查的位置。每个成员都很忙，任务仍然没有完成。

这也是理解 Multi-Agent 的起点：**增加执行者之后，必须同时设计责任如何分配、信息如何流动、状态如何更新，以及结果如何被验收。** Agent 的数量只是其中一个参数。

本文讨论基于大语言模型的多智能体系统，重点放在推理与执行阶段的协作。多智能体强化学习、机器人群体控制和经济博弈只作为相关背景，不在这里展开。

> **来源与边界**：本文综合官方工程文章、产品文档与研究论文，主要资料见文末。产品文档核对日期为 **2026 年 10 月 23 日**。权限管理案例、图示、任务协议和实验方案均为原创教学设计，未接入真实模型进行跑分；文中的工程建议不代表任何框架的默认行为。

## 先看单个 Agent：我们到底增加了什么

可以把一个执行型 Agent 理解为一个持续运行的决策循环：读取目标与当前信息，选择行动，调用工具，观察结果，再决定继续、调整或结束。模型负责其中一部分判断，外部程序负责实际执行、保存状态和约束权限。

因此，同一个模型可以支撑多个 Agent。前端 Agent 和测试 Agent 不一定使用不同模型，它们的区别可能来自各自收到的目标、能看到的上下文、可用工具，以及正在推进的任务。

反过来，连续调用三次模型，也不一定构成三个自主 Agent。如果程序固定执行“提取字段、生成文案、检查格式”，每一步都没有决定后续行动的空间，那么称为 LLM 工作流通常更准确。Anthropic 在基础模式文章中也用控制流程是否主要由预定义代码决定，区分工作流与 Agent。[来源：Building effective agents](https://www.anthropic.com/research/building-effective-agents)

这个区别会影响系统设计。固定流程可以依赖程序明确每一步的入口与出口；动态 Agent 则需要在执行中处理未知情况，系统必须为它提供预算、可观察状态和终止条件。

对于开头的权限功能，先定义几条业务要求：团队有 `owner`、`editor`、`viewer` 三种角色；只有 `owner` 能修改成员角色；任何角色都不能操作其他团队的数据；最后一个 `owner` 不能被移除。接下来才是如何安排执行者。

单 Agent 方案值得作为基线保留。如果它已经能稳定完成任务，再加成员就需要具体理由，例如某些调查能够并行、上下文过于庞杂，或者不同能力需要分别维护。仅仅给提示词增加“架构师”“工程师”“测试专家”的身份，不会自动产生这些收益。

## 架构名称很多，先拆开它们回答的问题

Supervisor、Swarm、Debate、Agent Teams 经常出现在同一张分类表里，但它们描述的并不完全是同一个维度。

Supervisor 主要回答谁来安排工作；并行执行回答哪些任务可以同时推进；Debate 回答如何让候选答案互相检验；Team 则常常还包含成员、任务与通信的运行机制。把这些词当成互斥选项，会让选型失去依据。

本文用下面六个维度分析系统。这是一套便于讨论的分析框架，不是统一行业标准。

| 维度 | 要回答的问题 | 常见选择 |
| --- | --- | --- |
| 控制权 | 谁决定下一步？ | 代码、中央调度者、分层负责人、成员自主决策 |
| 执行结构 | 工作如何展开？ | 串行、并行、分支、循环、动态任务图 |
| 通信方式 | 结果如何传递？ | 调用返回、点对点消息、广播、共享黑板 |
| 状态管理 | 谁知道什么？ | 私有上下文、共享任务、共享文件与数据库 |
| 协作策略 | 如何得到更好的结果？ | 专业分工、独立探索、评审、辩论、投票 |
| 部署边界 | 成员运行在哪里？ | 同进程、多进程、跨服务、跨组织 |

例如，一个系统可以由 Supervisor 管理任务，让前端与后端并行工作，通过共享接口文档对齐，再由独立评审者检查。它同时采用了中心化协调、并行执行、共享产物和评审循环。

同样，去中心化决策不意味着所有基础设施都去中心化。成员可能自主领取任务，却共用同一个任务数据库。讨论“有没有中心”时，需要明确说的是决策中心、消息中心，还是状态存储中心。

## 从固定流程到动态协作

### 流水线与 SOP：让每一步交付可用的东西

最直观的方案是安排一条流程：需求分析、接口设计、代码实现、测试验收。每个阶段完成后，将产物交给下一阶段。

这一模式的价值在于交付契约。接口设计阶段应该给出字段、错误码、权限规则和示例，而不仅是一段“使用 RESTful API”的建议。后续实现者才有稳定输入，测试者也能知道哪些行为必须成立。

MetaGPT 将 SOP 引入多 Agent 软件开发，是理解这种思路的一个代表性研究：它通过明确角色与流程组织协作，并强调中间结果的检查。[来源：MetaGPT 论文](https://arxiv.org/abs/2308.00352)

在权限案例中，流水线可以先产出权限矩阵，再定义接口，然后分别实现。风险也很直接：如果最初遗漏“不能移除最后一个 owner”，后续成员可能忠实地完成一套不完整设计。

因此，阶段之间需要检查门槛。例如接口设计进入实现之前，必须覆盖角色修改、跨团队拒绝与最后一个 owner 的行为。发现缺口后允许返回上游；有受控返工的流程不必被限制成一条永不回头的直线。

### Router：先选择合适的处理者

Router 根据请求内容选择后续路径。收到“按钮为什么不显示”，它可能转给前端；收到“用户能修改其他团队成员”，则转给后端与安全检查。

路由器不一定由 LLM 实现。已知错误码、明确的业务类型可以由规则处理，只有语义不确定时才需要模型判断。它也不必只选择一个目标，跨领域任务可以扇出到多个处理者。

Router 与 Supervisor 的区别在于承担的持续责任。一次分类之后就退出的节点是路由器；跟踪执行、补充任务、重新规划并验收的角色，承担了更广的协调职责。LangChain 的多智能体文档分别展示了路由、子 Agent 与交接等模式，适合对照这些边界。[来源：LangChain Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)

实际应用里，应给路由失败保留退路。权限漏洞同时表现为前端按钮和后端接口问题，如果分类只能二选一，就可能把系统问题切成两个没人负责的局部问题。

### 并行分解与汇总：分工和重复求解是两回事

并行至少有两种不同目的。第一种让成员完成不同部分，例如分别调查权限存储、接口鉴权和页面行为；第二种让多个成员独立检查同一问题，再比较答案。前者希望覆盖更多工作，后者希望获得不同候选。

![原创并行依赖图：权限契约分发给后端、前端与测试设计，较早结束的分支等待整合，最终在同一代码版本上验收](/assets/img/posts/multi-agent-to-agent-teams/parallel-dependencies.png)
_图 2：本文原创。条形长度与等待区间仅用于说明依赖，没有实测时间含义；图中摘录部分权限约束，完整要求以正文为准。测试用例可以提前设计，集成验收仍需要前后端产物。_

并行收益受依赖限制。后端接口还在反复变化，前端越早投入，后面可能返工越多。把接口契约先稳定下来，有时比再增加两个执行者更有效。

在一个简化模型中，串行耗时近似为各子任务耗时之和；全部独立且资源充足时，并行阶段近似由最慢子任务决定，再加上拆分、协调和汇总耗时。有依赖图时，应看关键路径，而不能简单用总时长除以 Agent 数量。模型限流、共享测试环境与合并冲突还会继续削弱收益。

### Supervisor–Worker：把动态任务拆解交给负责人

当要做哪些子任务不能提前完全确定时，可以让 Supervisor 先调查，再安排 workers。

它可能最初只派出一个成员定位权限逻辑，发现项目同时存在 HTTP API 和后台任务入口后，再追加第二条检查路径。worker 返回结果，Supervisor 判断是否足够、是否要追问，以及什么时候进入整合。

这套结构的收益来自动态分解和信息筛选。主 Agent 不必读完所有调查细节，但必须收到足以判断的证据。Anthropic 的 Research 系统采用主 Agent 与并行子 Agent 组织搜索，展示了独立上下文如何支持不同方向的探索。[来源：多智能体 Research 系统](https://www.anthropic.com/research/multi-agent-research-system)

这里最容易出现的薄弱点是汇报接口。worker 只说“鉴权逻辑正常”，Supervisor 很难判断它查了哪些入口。更好的返回包括检查范围、证据位置、未覆盖内容和发现的问题。

Supervisor 也可能成为瓶颈。如果每一个工具调用都必须经由它确认，它就变成串行调度器。合理的粒度通常是委派一个有验收标准的工作单元，让 worker 在范围内自行推进。

### 分层团队：增加管理层，也增加信息损耗

任务规模进一步扩大，可以让总负责人管理若干小组负责人，再由小组负责人安排成员。例如业务实现小组负责接口与页面，验证小组负责测试与审查。

分层有助于限制单个协调者需要处理的信息量，也让子系统内部的安排独立变化。但层级越多，信息越容易被摘要成模糊结论：“跨团队读取接口返回 200”经过几次转述，可能变成“存在少量权限问题”。

可以让每层都保留指向原始证据的引用，而不只传递总结。职责也应匹配系统边界：一个只转发消息、既不做判断也不验收的中间层，通常只会增加成本。

### Handoff：后续由谁继续处理

子任务调用与交接容易混淆。调用通常是“你完成这件事，把结果返回给我”；交接则是“接下来由你继续处理当前交互”。

在面向用户的支持系统中，通用助手识别出权限故障后，可以交给权限诊断 Agent，由它继续询问用户、检查设置并解释修复方案。移交的重点是后续控制权与必要上下文。

交接时需要带上已知事实、用户约束、已执行操作和未完成问题。只传一句“请处理权限问题”，新 Agent 就可能重复询问，甚至重复执行有副作用的操作。还应明确何时转回、何时结束，避免两个角色来回推送请求。

有些实现通过切换同一运行循环的提示词与工具集完成交接，并没有启动新进程。判断系统时应看控制与状态的实际变化，不宜从界面上的多个角色名推断部署结构。

### Peer-to-Peer 与 Swarm：成员可以自行寻找合作者

在对等协作中，成员可以根据局部信息寻找其他成员，不要求所有讨论都经过同一个主管。后端发现租户标识来源不一致，可以直接请求鉴权成员确认；测试成员发现接口行为与文档冲突，也可以直接联系实现者。

Swarm 这个词在不同项目中含义不完全相同。有时强调成员间交接，有时强调多个执行者的自主协作。阅读具体实现时，仍应回到谁决定任务、谁维护状态、谁宣布结束这三个问题。

对等通信能够减少中转，却可能增加总通信量。假设每一对成员都需要建立双向联系，潜在连接对数为 `n(n−1)/2`；这只是拓扑上的可能数量，不代表实际消息数必然如此增长。限制通信范围、按任务订阅信息，可以避免把每条发现都广播给所有人。

AutoGen 的早期论文把可编程多 Agent 对话作为组织协作的一种方式。需要注意，多 Agent 对话也可以由中央规则选择发言者，群聊界面本身不能证明系统是去中心化的。[来源：AutoGen 论文](https://arxiv.org/abs/2308.08155)

### Blackboard 与事件驱动：通过共享工作成果协作

另一个选择是把重要状态放进共享空间。Agent 不必逐个通知所有成员，而是提交接口版本、测试报告、待处理缺陷等记录，其他成员按需读取。这就是共享黑板思路在本例中的应用。

事件驱动可以与之配合，但两者并不等同。黑板关注共享的信息放在哪里；事件关注什么变化会触发后续工作。例如接口规范从草稿变成已确认，系统发出事件，唤醒依赖它的前端任务。

共享空间可以只是文件，也可以是数据库。真正需要设计的是更新规则：谁拥有某条记录、如何避免相互覆盖、旧结论怎样失效、事件重复到达怎么办。

在权限案例中，“接口已更新”应当指向一个明确版本。否则测试成员可能针对旧代码跑完检查，却把新版本任务标为通过。消息送达和状态一致，是两个需要分别保证的条件。

## 生成、评审、辩论与聚合：怎样利用多个候选

前面主要讨论工作怎样被安排。另一个维度是：多个成员怎样帮助形成更可靠的判断。

![原创协作策略图：评审通过反馈形成循环，辩论让独立候选互相质疑，MoA 将上一层输出传给下一层聚合](/assets/img/posts/multi-agent-to-agent-teams/collaboration-strategies.png)
_图 4：本文原创。三种结构分别突出反馈、信息交换和分层聚合。MoA 的每层可以有多个 Agent，图中省略层内展开；任何一种结构都不能用讨论一致替代外部验证。_

### 评审循环：先有标准，再谈改进

Evaluator–Optimizer 可以由一个成员生成方案，另一个检查，再根据反馈修改。权限功能的评审者应拿到业务要求、代码差异和测试输出，检查是否存在跨团队访问，而不只是评价代码是否整洁。

评审能够提供额外检查机会，但评审者也可能看错。若它只读实现者的总结，就可能重复实现者的盲点。因此，我更倾向于让它有独立取证能力，并把可以程序验证的要求交给测试。

循环还必须有边界。可以在硬性要求通过后结束，在预算耗尽或连续修改没有新证据时转交人工。无限“再改好一点”既不构成目标，也不构成可操作的停止规则。

### 辩论与投票：一致不等于正确

多 Agent 辩论通常先产生不同答案，再让参与者阅读、质疑和修正。相关论文研究了这一方法在推理与事实性任务中的表现，但这些结果需要放回论文的模型与任务条件中理解。[来源：Multiagent Debate](https://arxiv.org/abs/2305.14325)

在本文案例里，可以让两个成员分别审查“前端隐藏按钮是否足够”和“后端需要在哪些入口强制校验”，最后依据实际调用路径裁决。讨论有价值的部分是暴露遗漏的条件。

如果多个成员用了相同资料、相同提示词和相似模型，它们的错误可能高度相关。五个成员同意某个权限判断，不能替代一次真正的越权请求验证。先独立形成候选，再交换证据，也有助于避免过早跟随第一个答案。

投票还要求答案具有可比较的形式。对于自由文本方案，应先提取具体主张与约束，再讨论哪些成立；直接让另一个模型选择“听起来最好”的长回答，可能选中表达最自信的错误方案。

### Mixture-of-Agents：在输出层逐层聚合

MoA 采用分层结构，一层中的多个模型生成回答，下一层利用前一层的输出继续生成，最终形成聚合结果。[来源：Mixture-of-Agents 论文](https://arxiv.org/abs/2406.04692)

它与模型内部的 Mixture-of-Experts 处在不同层级。这里组合的是多次模型调用产生的输出，并非把输入 token 路由给一个模型内部的参数专家。这种组合也不必包含长期运行、调用工具的执行型 Agent。

放到权限设计里，可以先产生几个方案，再由聚合者整理它们的取舍。但如果所有候选都遗漏“最后一个 owner”的约束，聚合步骤并没有可靠理由凭空补齐。聚合者需要回看原始要求，并保留候选之间的实质冲突，不能只把它们润色成一篇统一叙述。

## Agent Teams：把成员、任务与通信组织起来

泛指的 agent team，是多个 Agent 围绕共同目标协作；Claude Code 的 Agent Teams 则是一个具体产品功能。它与 Multi-Agent 是包含关系，产品名称本身不定义唯一的协作算法。

截至本文核对日期，Claude Code 官方文档仍将 Agent Teams 标为实验性、默认关闭。其基本组成包括负责人、独立队友、共享任务和成员消息。另一个版本细节是：当前具名 subagent 也可以互相发消息，因此“能否互发消息”不能作为两者的绝对分界。[来源：Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams)

从设计角度看，我更关注它是否支持成员围绕同一工作持续推进：一个成员完成阶段任务后，能否保留相关状态参与后续调整；其他成员是否能知道任务归属与依赖；负责人如何把各人的产物整合为最终交付。

下面是一个教学上的团队设计，不是 Claude Code 内部实现图。

![原创团队协调图：负责人向三名成员分派工作，成员横向交换发现，将带有版本和负责人信息的任务写入共享记录，负责人再读回状态组织整合](/assets/img/posts/multi-agent-to-agent-teams/team-coordination.png)
_图 5：本文原创的团队设计，非 Claude Code 内部实现图。紫色表示分工，蓝色表示成员通信，绿色表示共享状态流动；任务字段来自本文示例。横向连线只展示部分联系，不限制谁可以通信。_

这个团队可以按下面的过程工作：负责人先明确权限要求和改动范围，后端成员提出接口契约，前端成员确认页面需要的字段，验证成员提前设计越权测试。契约稳定后，前后端并行实现；发现变更时，通知受影响成员并更新任务依赖；最终在同一代码版本上集成验收。

从传统 Supervisor 方案出发，也能逐步增加这些能力。两者并不存在不可跨越的理论边界。更有用的比较是：系统提供了多少独立执行、持续通信、任务协调和生命周期管理能力，以及为此付出了多少成本。

### 什么时候值得用团队

我会优先考虑三种情况：任务存在可以分别推进的部分；执行期间需要跨成员交换新发现；最终成果有办法整合并独立验证。权限功能的前后端协作比较符合这三个条件。

如果只是查一个配置值，调用一个聚焦的子任务通常就够了。如果多人必须持续修改同一段鉴权逻辑，增加成员可能放大冲突。这时可以让一个成员负责修改，其他成员分别调查、提出方案或评审。

独立上下文也不等于已经实现安全隔离。成员是否共享文件、凭据和网络权限，取决于运行环境。真正的写入边界需要由目录权限、工作区、工具策略等机制落实，不能只在角色提示词里写“你只负责前端”。

### 同样叫 Team，协调方式可以完全不同

Anthropic 的编译器实验提供了一个有价值的对照。作者使用 16 个 Agent，在独立容器和 Git 副本中工作，通过任务文件认领与代码同步组织协作，并明确说明该研究原型没有中央编排 Agent。产物仍存在性能和兼容性等限制。[来源：Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/research/building-c-compiler)

这与带有负责人和成员消息机制的产品形态不能直接画等号。前者说明，共享产物与认领规则也能组织团队；后者展示了另一种协调入口。读案例时，应追问具体依靠什么对齐状态、解决冲突和验证进展，而不能只比较成员数量。

## 一个团队运行起来，还需要哪些机制

架构图只能画出关系，无法自动保证这些关系在失败、重试和并发情况下仍然成立。下面把权限案例推进到可以实现的程度。

### 任务协议：从“帮我做后端”到可检查的工作单元

“你负责后端”没有告诉成员边界和完成条件。一个更实用的任务描述应该包含输入版本、目标、允许修改范围、依赖、产物与验收证据。

下面是示意协议，字段由本文定义，不对应任何框架 API，也未执行。

```yaml
task_id: permission-api-01
goal: 实现团队成员角色修改接口
input_revision: contract-v2
depends_on: [permission-contract-02]
allowed_paths:
  - backend/team_permissions/
  - tests/team_permissions/
deliverables:
  - 代码补丁及对应版本标识
  - 测试命令、退出码与结果文件
acceptance:
  - owner 可以修改本团队成员角色
  - editor 和 viewer 的修改请求被拒绝
  - 跨团队请求被拒绝
  - 最后一个 owner 不能被降级或移除
completion_policy: 提交证据后由独立验收步骤确认
```

字段本身只是信息载体。`allowed_paths` 如果没有执行侧检查，就只是一项约定；`acceptance` 如果没有验收程序或评审步骤，也不会自动变成保证。任务协议的作用，是让运行系统知道应该检查什么。

### 状态机：完成需要经过哪一步

建议把“执行者做完”与“系统验收通过”分开记录。前者可以提交补丁，后者需要验证补丁在目标版本上满足要求。

![原创任务生命周期图：可领取的任务经原子认领进入执行，提交产物后接受验收，通过才算完成，受阻与验收失败分别回到可调度状态](/assets/img/posts/multi-agent-to-agent-teams/task-lifecycle.png)
_图 6：本文原创的简化状态与验收示意。菱形表示验收决策门槛；实际系统可为待验收另设状态。取消、不可恢复失败、预算耗尽与超时等分支未在图中展开。_

这里的“原子认领”需要由存储操作保证。例如只有当任务状态仍为 Ready 时，才允许同时写入负责人并切换为 Running。先读取“无人认领”，再分别写入，两名成员就可能同时以为自己获得了任务。

如果采用租约回收失联任务，还要处理旧成员恢复后继续提交的问题。可以为每次认领分配递增代次，提交结果时检查代次是否仍然有效。否则任务虽然重新分派，旧执行者仍可能覆盖新结果。

这些机制主要解决协调正确性。并非每个小型本地原型都需要数据库租约，但只要系统允许并发认领和故障恢复，就需要明确相应语义。

### 通信协议：消息送达之后还要发生什么

“我已经通知前端了”最多说明发送动作发生过。前端是否收到、理解、更新实现并重新验证，需要不同证据。

对于重要变更，可以让消息携带 `task_id`、消息标识、接口版本、变更摘要和需要的响应。接收方确认采用 `contract-v2` 后，相关任务才解除阻塞。一般讨论不必逐条确认，但会改变接口、依赖和验收条件的信息应写入共享记录。

采用消息队列时，还要假定消息可能重复。重复收到“重新测试”通常只是浪费资源；重复执行“创建生产账号”则可能产生真实副作用。操作幂等性应由工具或业务服务实现，例如依据稳定的操作标识去重，而不依赖模型记得自己做过。

### 上下文管理：摘要要能回到原始证据

不必让所有成员读完整聊天记录。后端需要权限模型和接口约束，前端需要字段及错误行为，验证者需要用户要求和可复现环境。

但摘要应保留事实与推断的区别。相比“存在越权漏洞”，更可用的记录是：“在版本 X 上，viewer 使用请求 Y 访问另一团队成员接口，得到 200；复现脚本位于 Z；尚未检查批量接口。”

这段摘要同时表达结论、证据和范围。接收者可以继续验证，也能避免把“未检查”误解为“没有问题”。共享代码变更后，还应将旧验证标记为针对旧版本，不能让它继续为新版本背书。

![原创上下文证据图：私有工作轨迹提炼成含结论、版本、观察、复现与未查范围的证据包，验收者可以沿引用追溯原始记录](/assets/img/posts/multi-agent-to-agent-teams/context-evidence.png)
_图 7：本文原创。证据包中的 `patch-v3`、`repro-01` 和 `test-report` 是教学标识，不是实际运行结果。共享信息经过压缩，但仍需能够追溯。_

### 工作区隔离与集成：各自通过不等于一起通过

对代码任务，可以使用独立分支或 worktree 降低直接覆盖风险。共享目录也能工作，但需要更严格的文件归属与修改顺序。

隔离并不会消除语义冲突。两份补丁可能都能干净合并，却分别改变了同一个字段的含义。因而每个成员的局部测试之外，还要在整合后的版本上验证关键流程。

对于权限案例，最终测试应通过真实的请求路径验证跨团队拒绝，并检查最后一个 owner 的规则。如果存在两个并发降级请求，还需要检查事务与并发控制是否守住不变量。这已经超出了“前端按钮正确显示”和“后端单个函数测试通过”的范围。

## MCP 与 A2A：连接解决到哪一层

团队内部可以用函数、文件或队列通信。只有当 Agent 需要跨服务或组织协作时，协议互操作的问题才会更加突出。

MCP 主要提供模型应用接入工具与资源的统一方式；A2A 面向不同 Agent 系统之间的发现与协作。官方将两者描述为互补关系。[来源：A2A 与 MCP 官方对比](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)

在权限案例里，开发 Agent 可以通过 MCP 接入代码与测试工具；若它需要委派给另一个团队独立部署的安全审查 Agent，可以考虑 A2A 这样的协议。这只是部署示例，不是实施多智能体的必选步骤。

![原创协议边界图：本地开发 Agent 经 MCP 接入代码与测试工具，经 A2A 向另一团队独立部署的安全审查 Agent 委派任务并取得报告](/assets/img/posts/multi-agent-to-agent-teams/protocol-boundaries.png)
_图 8：本文原创，依据前述官方协议定位构造的部署示例。虚线划分应用边界，不表示唯一网络部署方式；工具服务也可以远程部署，接入协议不替代任务验收。_

协议统一了交流方式，仍需要业务定义什么叫“安全审查完成”。远端服务返回任务完成，并不自动说明本地的全部验收条件已经满足。调用方仍应检查产物、检查范围与目标版本。

还要区分传输可信和内容可信。消息确实来自某个成员，并不意味着内容中的建议获得了执行授权。检索文档、工具输出和其他 Agent 转述的文本，都可能包含错误或诱导性指令；执行权限应由系统边界控制。

## 为什么 Agent 越多，结果不一定越好

多智能体的失败往往发生在成员之间。一个成员没有拿到最新约束，另一个成员忽略它的反馈，最后负责人根据不完整总结提前结束。单独查看每次模型回答，未必能看到整个失败链。

MAST 研究把失败归为系统设计、Agent 间失配与任务验证三类；其论文 v3 介绍了覆盖 7 个框架、1,600 多条标注轨迹的数据集。这是特定系统与任务上的研究材料，不应据此推出所有多智能体系统的统一失败率。[来源：Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657)

回到本文案例，可以把常见症状对应到可检查的机制。以下是案例分析，不是原论文分类表的逐项复述。

| 症状 | 可能缺失的机制 | 可以收集的证据 |
| --- | --- | --- |
| 两个成员同时重写同一模块 | 认领与修改范围约束 | 任务归属、文件修改时间与补丁 |
| 前后端对角色名称理解不同 | 版本化接口契约 | 实际采用的契约版本 |
| 同一问题反复讨论 | 决策记录与停止条件 | 新增证据数、重复消息与重试原因 |
| 多人一致判断错误 | 独立信息源或外部验证 | 各自资料来源与反例测试 |
| 每个任务通过，产品仍失败 | 集成验收 | 整合版本与端到端测试结果 |
| 成员结束后任务失联 | 生命周期管理 | 运行状态、超时与恢复记录 |

这些问题不能都靠“请认真协作”修复。任务重复认领需要并发控制，旧证据失效需要版本关联，越权执行需要权限限制。提示词可以帮助成员理解规则，运行系统负责让关键规则能够被执行和检查。

## 如何证明团队真的值得：一个待实施的实验

如果只比较低预算单 Agent 与高预算团队，很难知道收益来自协作，还是来自更多模型调用。为了区分这两点，可以设计下面的实验。**本节没有实测分数，也不声称某个架构已经胜出。**

准备同一产品的固定起始版本，构造若干任务：边界清楚的小修复、可并行的跨模块功能、依赖很强的重构，以及需要调查多条线索的故障。每个任务预先定义验收条件，测试不依赖 Agent 自己宣称成功。

比较四组系统：基础单 Agent；增加推理或采样预算的单 Agent；由 Supervisor 调度的 workers；支持持续成员通信与共享任务的 Team。单 Agent 的候选选择与验证同样计入预算，不能把它的额外开销忽略。

保持模型版本、工具权限、起始代码、任务描述与外部环境尽量一致。若团队使用异构模型，另设实验组；否则模型能力差异会混入架构差异。每次尝试从干净状态开始，对同一任务重复运行，并报告样本量、成功次数与波动。

![原创评估设计图：同一任务快照分发给基础单 Agent、增加预算的单 Agent、Supervisor 与 workers、持续协作 Team，最终由统一独立验收比较结果](/assets/img/posts/multi-agent-to-agent-teams/evaluation-design.png)
_图 9：本文原创的待实施实验方案。图中没有准确率、耗时或成本成绩；四组采用相同任务、起始环境与验收规则，以便进一步比较预算和协作结构的影响。_

| 指标 | 记录方式 | 避免的误判 |
| --- | --- | --- |
| 任务成功率 | 最终版本通过预定义验收的比例 | 把“自报完成”当成功 |
| 总成本 | 累计模型调用、工具与执行资源成本 | 只统计负责人消耗 |
| 完成耗时 | 从开始到最终验收的墙钟时间 | 把等待和整合排除在外 |
| 协调负担 | 消息、重复任务、冲突与返工记录 | 把成员忙碌当有效进展 |
| 人工介入 | 次数、原因及处理时间 | 把大量人工兜底算作自主完成 |
| 恢复能力 | 注入成员超时后能否正确继续 | 只验证顺利路径 |

可以做两种互补比较：固定成本上限，看谁完成得更好；固定目标质量，看谁所需成本与时间更少。对于硬截止时间的产品，还应固定时间上限，统计截止前完成的任务。

进一步做消融：保留团队但关闭横向消息、去掉独立评审，或将共享历史改成按需摘要。每次只改变一个因素，才能逐步判断性能变化来自哪里。

一次演示适合展示交互方式，重复实验才有机会回答可靠性问题。即使团队在跨模块任务中胜出，也不能推断它在所有短任务上都值得使用。

## 把架构选择落到具体问题

面对一个新任务，我会按下面的顺序判断。这里给出的是工程启发，需要用实际任务验证。

| 当前遇到的问题 | 优先尝试的结构 | 先确认什么 |
| --- | --- | --- |
| 步骤已知，输入输出明确 | 固定工作流或流水线 | 阶段契约与失败分支 |
| 请求属于不同专业领域 | Router | 误路由和跨领域退路 |
| 子任务独立、汇总标准清楚 | 并行 workers | 是否真的可独立验收 |
| 执行中才知道要拆哪些任务 | Supervisor | 主管能否判断结果与预算 |
| 后续对话需要专业角色接管 | Handoff | 控制权与上下文移交规则 |
| 多个成员需要持续互相调整 | Team 或混合架构 | 共享任务、冲突处理与整合责任 |
| 要利用多个候选提高判断质量 | 评审、投票或辩论 | 候选差异与外部验证能力 |
| 需要委派给独立部署的服务 | 跨系统 Agent 协作 | 身份、协议、产物与失败语义 |

权限管理功能的一个合理起点，是先由一个 Agent 明确要求与接口契约，再安排前后端独立实施，由验证者检查整合结果。只有执行过程中确实需要反复交换发现，才增加持续团队通信。若主要瓶颈在同一份鉴权代码上，就保持单一修改负责人，让其他成员提供调查和验证。

当最后一个 `owner` 不能被错误移除、跨团队请求被可靠拒绝、前后端使用同一版接口时，团队才交付了用户要的功能。架构图里的每个角色，都应该能解释自己怎样帮助这些结果成立。
