Agent 说“已经完成”，离任务真的完成还有多远？如果它要交付的是一份报表，回答通顺只是最容易观察的一层。文件有没有生成、内容是否正确、生成期间有没有改坏数据，才决定这次执行能否被接受。

这篇文章从 Anthropic 的评估方法文章出发，用一个原创的报表案例讨论如何把“感觉好用”变成可检查的验收条件。

> **阅读来源**：[Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)，Anthropic，2026 年 1 月 9 日。作者：Mikaela Grace、Jeremy Hadfield、Rodrigo Olivares、Jiri De Jonghe。
>
> 本文是独立技术解析。下面的订单数据、验收规则、代码与图解均为本文构造的教学示例，不是 Anthropic 的实现或实测结果。

## 原文给我的三个切入点

原文区分运行轨迹与最终结果，将代码、模型和人工判断结合起来，并强调通过多次运行观察可靠性。它还区分探索能力上限的评估与防止退步的回归评估。[来源：原文](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

我的理解是：评估最值得投入的地方，在于把产品承诺落实为证据。下面不按原文章节复述，而是从一份可以交付、也可以验收的报表开始。

## 先把任务写到足以判定对错

假设用户的要求是：

> 将本次提供的订单快照中所有 `paid` 订单导出到 `report.csv`，只包含 `order_id` 和 `amount_cents` 两列，按订单号升序排列。不要修改订单数据；完成后告知文件路径与订单数。

评估环境放入这份固定输入：

| order_id | status | amount_cents |
| --- | --- | ---: |
| A01 | paid | 12000 |
| A02 | cancelled | 8000 |
| A03 | refunded | 5000 |

预期 CSV 为：

```csv
order_id,amount_cents
A01,12000
```

我刻意采用“整数分”，避免把浮点精度和金额格式混在一起；采用固定快照，避免订单在执行期间变化；明确排序，避免评分器私自假定某种顺序。这里的重点不在三个字段，而在于：**测试中的每个硬要求，都应该能回到任务描述里找到依据。**

再考虑一个容易被忽略的变体：输入没有任何 `paid` 订单。此时生成只有表头的文件，是合理的成功结果。若测试只写了“文件不能空”，就可能拒绝这个正确答案。设计验收规则时，需要同时写出正常情况和边界情况。

### 这一轮究竟在评估什么

对这个例子，我会把记录拆成以下几层。这是本文的案例映射，便于落地时确定每份数据存在哪里。

| 记录 | 本例中的具体内容 | 为什么单独保存 |
| --- | --- | --- |
| 任务 task | 输入快照、用户要求、验收规则 | 确定本轮的承诺 |
| 尝试 trial | 对同一任务从干净环境执行一次 | 区分偶然成功与稳定成功 |
| 轨迹 transcript | 查询、文件写入、工具返回、最终回复 | 解释问题发生在哪里 |
| 结果 outcome | 实际 CSV、订单库状态、文件可访问性 | 验证用户是否拿到了正确产物 |
| 评分 grader | 字段检查、内容比较、写入审计 | 把证据转为分项结论 |
| 测试集 suite | 正常订单、空结果、异常权限等案例 | 防止只优化一个演示 |

还应区分两套运行机制：一套让 Agent 调用模型和工具，另一套负责准备测试环境、启动尝试、收集证据与评分。它们可以共享组件，但职责不同。

一次回答的检查通常拿到输出就能评分；执行型任务还包含“行动—观察—再行动”的循环。比如，首次查询漏掉一页订单，Agent 可能继续用不完整数据计算总额，再把错误数字写进回复。评估必须保留这些中间结果，才能看出错误在哪一步开始传播。另一方面，Agent 也可能通过不同查询方式生成同样正确的 CSV，不能把预想的操作路径当成唯一答案。

如果升级模型时顺便扩大了工具权限、延长了超时时间，分数上涨就不能全部归因于模型。我的做法是为每次评估记录模型标识、提示词版本、工具版本、权限配置、任务集版本和评分器版本。**比较对象是这套具体配置下的系统。**

## 把“说过什么”和“留下什么”分开核对

_图 1：本文原创。图中的 CSV 是教学示例；硬条件先行是本例的评分设计，并非所有 Agent 任务都必须采用同一顺序。_

[下载可编辑 Excalidraw 源文件](/assets/diagrams/anthropic-agent-evals/evidence-flow.excalidraw)

图里的两条证据链各有盲区。

只看最终文件，可能发现报表内容正确，却漏掉 Agent 曾试图更新订单状态。只看工具调用，可能看到它执行了文件写入，却不知道文件被后续步骤覆盖，或保存在用户无法取得的目录。

因此，本例需要三种检查：

1. **产物检查**：在声明的交付位置重新读取 CSV，检查列、行、顺序及重复项。
2. **状态检查**：比较运行前后的订单快照，检查业务数据是否改变。
3. **操作检查**：查看数据库审计，确认没有写入尝试。即便写入被权限拒绝，也应单独标记指令遵循问题。

状态检查还不是万能证据：如果 Agent 先修改再恢复数据，前后快照可能相同。因此，“最后没变”和“从未写入”应当采用不同检查。实际产品里，我会同时使用只读数据库账号限制能力，并用评估发现越界倾向；评估不能代替权限控制。

### 一个最小的产物评分函数

下面代码只演示 CSV 的判定方式。它不实现模型调用、数据库审计或整套评估框架。

```python
import csv


def grade_report(csv_path, snapshot):
    expected = [
        {"order_id": row["order_id"],
         "amount_cents": str(row["amount_cents"])}
        for row in sorted(snapshot, key=lambda row: row["order_id"])
        if row["status"] == "paid"
    ]
    try:
        with open(csv_path, encoding="utf-8", newline="") as stream:
            reader = csv.DictReader(stream)
            columns_ok = reader.fieldnames == ["order_id", "amount_cents"]
            actual = list(reader)
    except (OSError, UnicodeError, csv.Error) as error:
        return {"passed": False, "reason": type(error).__name__}

    return {
        "passed": columns_ok and actual == expected,
        "columns_ok": columns_ok,
        "rows_ok": actual == expected,
    }
```

这里比较列表而非集合，是为了保留顺序与重复行的信息。这个选择依赖任务明确规定排序；如果用户允许任意顺序，评分器也应调整，不能拿自己的偏好处罚有效结果。

另一个工程边界是可信性：期望结果应从评估端保存的原始快照计算，评分代码与快照不能让被测 Agent 任意改写。否则它修改“标准答案”后，也可能拿到通过结果。

## 三种评分方式，分别承担什么责任

针对本例，我会这样分配工作，而不是让一个模型给出笼统的“85 分”。

| 方式 | 负责的问题 | 本例的检查 | 需要提防什么 |
| --- | --- | --- | --- |
| 代码 | 可精确定义的条件 | CSV 是否等于预期，数据库是否出现写入 | 规则写错、缺边界案例、检查对象不可信 |
| 模型 | 语言表达与解释是否合适 | 回复是否准确说明订单数、路径和异常 | 被漂亮措辞影响、缺证据还强行打分 |
| 人工 | 标准本身是否合理 | 审核模型与代码的争议判定 | 判断口径不一致、审核成本 |

模型评分的输入至少要包含任务、相关工具结果、最终回复和检查证据。仅给最终回复，让它判断“是否完成”，等于让评分器猜测文件系统里发生了什么。

可以把模型评分问题拆成独立条目，例如：“回复中的订单数是否与已验证 CSV 一致？”“遇到权限错误时是否如实说明？”证据不足时返回 `unknown`，并在统计中单独展示覆盖率。把 `unknown` 悄悄当作通过，会掩盖评估盲区；全部当作任务失败，则可能混淆证据采集问题与 Agent 问题。

### 硬门槛与部分得分并不矛盾

本例中的产品验收可以定义为：

```text
任务通过 = CSV 正确 AND 无写库尝试 AND 文件可交付
```

同时保留“是否选对订单、是否写出文件、是否解释清楚”等分项。这些部分得分用来定位进步，不能抵消写库越界等硬失败。

评分报告因此有两个用途：面向发布决策的通过条件，以及面向研发的诊断信息。将二者揉成一个加权总分，容易出现“解释得很好，所以数据导错也够分”的结果。

## 一次成功，不能代表每次可靠

下面用独立的概率例子理解重复运行：假设某个固定任务每次成功概率为 80%，各次尝试独立，环境和配置不变。

至少成功一次，与每次都成功，是两个不同事件：

$$
P(\text{至少一次成功}) = 1-(1-p)^k
$$

$$
P(\text{全部成功}) = p^k
$$

| 尝试次数 k | 至少一次成功 | 全部成功 |
| ---: | ---: | ---: |
| 1 | 80% | 80% |
| 3 | 99.2% | 51.2% |
| 5 | 99.968% | 32.768% |

这对应理解 `pass@k` 与 `pass^k` 的两个方向。上述数值是公式计算，不是模型测试成绩。

![同一组五次尝试，在至少一次成功规则下通过，在全部成功规则下不通过](/assets/img/posts/anthropic-agent-evals/trial-rules.png)
_图 2：原创示意。两种规则检查同一组尝试；单组示意不用于估计总体概率。[可编辑源文件](/assets/diagrams/anthropic-agent-evals/trial-rules.excalidraw)。_

对交互式报表工具，如果用户愿意重试，而且系统有可信校验器选出正确文件，多次尝试可能有价值。对每天自动发出的报表，“五次里面总有一次成功”就不是合适的服务承诺；用户关心的是今天收到的这一份是否可靠。

还要注意两个统计陷阱。第一，不应把所有任务的平均成功率直接代入公式：简单任务和困难任务的概率不同，先求平均再做幂运算会改变结果。第二，如果多次运行共用损坏的缓存或不可用服务，独立性假设已经失效。实际报告应保存逐任务、逐尝试结果，再按明确方法聚合，并报告样本数与不确定性。

为了衡量重试的实际价值，我还会记录每个**成功交付**消耗的总时长、调用数和费用，包含失败重试的成本。否则提高重试预算可能只让成功率看起来更好，却让产品更慢、更贵。

## 从这个案例长出一套可维护的评估

### 先对齐原文的路线，再明确自己的交付物

原文路线编号是 **0—8，共九步**；起点是尽早开始，建议初期从真实失败中收集 20—50 个任务。[来源：Anthropic 的从零搭建章节](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

这里的数量是启动建议，不是统计可靠性的保证。对低频严重错误或细小改进，仍需要根据目标补充样本和重复次数；关键是先建立可运行的闭环，再逐步扩展覆盖。

下表左列是路线索引，右列是本文为报表案例设计的具体交付物，便于把建议变成可执行工作。

| 步骤索引 | 本文案例要交付什么 |
| --- | --- |
| 0．尽早开始 | 在接入新模型前，写出“只导出已付款订单”的验收约定 |
| 1．收集已有手工检查 | 将客服反馈中的漏行、错金额、文件不可访问转为任务 |
| 2．明确任务与参考解 | 固定输入、产物位置、排序规则，提供人工确认过的 CSV |
| 3．平衡任务分布 | 同时覆盖有结果、无结果、可写目录、权限不足 |
| 4．稳定运行环境 | 每轮独立目录和快照，记录工具权限、超时及资源配置 |
| 5．设计评分器 | 产物与审计作硬检查，表达作分项，准备评分器反例 |
| 6．检查运行记录 | 对每次争议留下“证据—判定—归因”，区分系统与评分错误 |
| 7．关注能力饱和 | 简单导出稳定后保留回归，再加入关联查询等新任务 |

### 实施时，优先消除这些假信号

以下是我会采用的检查方式，不是 Anthropic 的任务模板。

**先写一份人工可完成的参考产物。** 对上面的输入，手工写出正确 CSV，并确认评分器接受它。再放入漏行、重复行、错金额、错列名等坏样本，确认评分器拒绝。评分器也需要被检验，不能因为它是代码就默认正确。

**再按风险补充成对案例。** 有已付款订单时应导出，无符合条件的订单时应给出合法空结果；权限允许时应生成文件，权限不足时应如实报告。不要为了提高某种行为的触发率，只测试它应该发生的一侧。

**让每次尝试从干净环境开始。** 新建输出目录，恢复输入快照，清除上轮产物与缓存，保持权限一致。数据库连接失败等基础设施问题单独归类，不能静默删掉失败样本，也不宜全部算作模型能力下降。

**先比较同一批任务上的新旧版本。** 保存所有版本信息，按任务对照结果。某个版本的通过率从 8/10 变成 9/10，只说明这次观测多通过一个任务；不能仅凭这个差异宣称稳定提升。

**区分已经承诺的能力和正在探索的能力。** 对简单筛选导出，维护严格回归集；对多表关联、复杂口径澄清等新需求，另设探索集。当探索任务足够稳定并成为产品承诺，再纳入回归保护。若某套题长期全对，它仍能防退步，但需要新任务才能继续观察能力差异。

**保留失败证据，明确维护者。** 产品负责人维护验收口径，领域人员贡献案例，工程人员维护环境与评分实现。任务变更时同步更新参考产物和版本记录，避免同名指标实际上测了不同东西。

还有三类异常值得在启动阶段主动排查。

- **所有尝试都失败**：先让参考解走完整条评分链，检查文件路径、权限和比较规则。如果说明允许任意输出目录，评分器却只读一个固定路径，修复对象应是契约或评分器。
- **第二次明显更容易**：检查上次 CSV、缓存查询结果、共享工作区和 Git 历史是否泄漏答案。仅删除一个输出文件不一定恢复了完整初始状态。
- **换了实现方式就被判错**：例如 Agent 用流式写出代替先拼完整表格，只要满足同一交付约定，就不应因为工具调用顺序不同而失败。但身份校验、只读限制等明确要求仍必须检查。

我会把这些原因作为独立字段记录，而不是全部记为“模型失败”。对评分器的修订也要保留版本，并用新规则重评旧产物，确认分数变化到底来自 Agent 进步还是裁判变化。

原文有一句值得贴在评估面板旁边的话：

> “Read the transcripts!”
>
> ——[Anthropic 原文结论](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

对本例来说，看到 `rows_ok=false` 后，还应继续追问：查询结果就错了，还是 CSV 序列化出错？Agent 是否收到工具错误？参考快照是不是取错版本？只有把错误归因到可修复的环节，分数才会指导下一步工作。

## 四类 Agent，分别怎样评估

报表任务比较容易找到客观产物。把这套思路迁移到其他任务时，我会先问“用户最终验收什么”，再决定检查方式。下面是本文自拟的迁移例子。

| Agent 场景 | 自拟任务 | 我会优先收集的证据 |
| --- | --- | --- |
| 编码 | 给 CSV 导出器增加空结果支持 | 新增边界测试、原有测试、实际导出文件与差异 |
| 多轮对话 | 用户逐步澄清报表口径 | 每轮新增约束、最后确认的条件、实际文件是否一致 |
| 研究 | 比较三种报表工具 | 结论对应来源、比较维度的覆盖、资料日期与限制 |
| 图形界面操作 | 在网页后台下载报表 | 实际下载文件、筛选状态、会话权限、后台数据变化 |

### 编码 Agent：修好新问题，也保住旧行为

[SWE-bench 的评估文档](https://www.swebench.com/SWE-bench/guides/evaluation/)描述的核心流程是把生成补丁应用到仓库，再在容器环境运行测试。这个设计让“提交了看起来合理的代码”和“修复确实生效”可以分开验证。

迁移到本文的导出器，我会检查两组测试：新增的空结果案例原本失败、修改后通过；原有普通订单导出修改后仍通过，也就是常说的 `fail-to-pass` 与 `pass-to-pass`。除此之外，检查补丁是否擅自删测试、硬编码样例订单、改动无关文件。测试通过是功能证据，但不自动保证可维护性。

对于“写一个可运行的导出命令”这样的端到端任务，还要实际启动程序，核对退出码、参数、权限错误和生成文件，不能只验函数。可结合 [Terminal-Bench](https://www.tbench.ai/)继续了解终端任务评估；本文不引用会随版本变化的榜单分数。

### 对话 Agent：用户会改变条件，也可能参与操作

[τ-bench 论文](https://arxiv.org/abs/2406.12045)使用模型模拟用户，配合领域工具与规则，并比较对话结束时的数据库状态。[τ²-bench](https://arxiv.org/abs/2506.07982)进一步讨论用户与 Agent 都能操作共享环境的情形。因此，评估对象包含协作是否奏效，不能只看 Agent 单方的操作。

在报表例子里，可以让模拟用户先说“导出订单”，被询问后再补充“只要已付款的”，最后在下载失败时报告错误。测试应保存每轮新约束，核对 Agent 是否澄清、是否记住修订、最终是否交付。对话结束条件、最大轮次、用户可见信息也要固定，否则不同版本面对的任务难度可能不同。

模拟用户不能拿着完整标准答案主动提示 Agent。我的做法是把“用户掌握的信息”和“评分器掌握的信息”分开，并抽查模拟器是否越过这一边界。说明质量可由结构化量表评判，文件是否正确仍交给实际产物检查；礼貌不能代替完成任务。

### 研究 Agent：找到答案与完成研究是两种能力

[BrowseComp 论文](https://arxiv.org/abs/2504.12516)选择难查找、但答案较短且容易核验的问题，并明确承认它没有覆盖长回答和含糊需求等全部真实场景。这对自建评估很有启发：一个擅长找到冷门事实的系统，未必能写好一份有取舍的研究报告。

如果任务是比较三种报表工具，我会先给出必答维度，例如导出格式、权限模型、部署条件和资料日期，再把每条结论连到支持它的来源。需要分别检查：事实正确吗，关键维度漏了吗，引用真的支持这句话吗，多个来源冲突时有没有交代？

对有明确答案的问题，可以精确匹配或规范化后比较；对建议质量与综合判断，应给领域评审员相同的证据包并校准口径。资料持续变化时，保存抓取时间和必要的证据快照，否则“上次正确、这次错误”也可能只是来源更新。引用数量只能反映形式，不能直接代表可信度。

### 计算机操作 Agent：界面反馈之外，还要核对应用状态

[OSWorld 项目](https://osworld-v1.xlang.ai/)提供真实计算机任务环境以及任务准备、执行式评估脚本。对网页场景，也可参看 [WebArena](https://webarena.dev/)。这类评估需要把页面操作与真实结果连起来。

例如后台出现“导出成功”，但浏览器阻止了下载；或者下载到的是上一次筛选条件的文件。只截取提示框都会误判。本文的报表任务应同时检查当前筛选条件、文件下载完成、CSV 内容，以及订单状态未被更改。

为了让比较可重复，我会固定窗口尺寸、登录身份、起始页面、应用数据与下载目录，明确异步任务的等待上限。遇到浏览器崩溃或网络断开时留下基础设施故障标记，再决定是否重跑。不要悄悄无限重试，让执行时间和可靠性问题从报告里消失。

浏览器工具选择还有成本差异：结构化页面读取有助于核对大量字段，截图有助于理解视觉状态；哪种更省时、更省 token，应在自己的页面和工具上测量，不宜写成通用定律。

## 离线通过之后，还缺什么

我的报表测试用的是固定快照。真实环境可能新增状态值、字段权限改变，或者用户开始要求不同业务口径。因此，本地评估通过只说明系统满足了这套已知案例。

上线后的失败率、用户纠错、人工抽查和有条件的对照实验，分别提供不同证据。尤其要追踪“离线通过，但用户仍判定失败”的案例：它可能暴露了任务定义之外的需求，而不只是某条提示词不够好。

对于这个服务，我会把观测方法分工如下，避免给一个指标过多含义：

| 方法 | 本例回答的问题 | 单独使用时的盲区 |
| --- | --- | --- |
| 离线自动评估 | 已知输入下是否符合交付契约 | 覆盖不到尚未出现的业务口径 |
| 线上监测 | 下载错误、超时、成本是否异常 | HTTP 成功不保证报表含义正确 |
| A/B 对照 | 某次改动是否改善用户完成率 | 需要合适的样本与实验设计，不能解释全部原因 |
| 用户反馈 | 用户实际在意哪些失败 | 主动反馈不是所有用户的随机样本 |
| 人工读轨迹 | 错误在哪一步发生 | 抽查有限，不能替代全量统计 |
| 系统性人工评审 | 不同评审者对报告质量能否达成一致 | 成本较高，需要共同量表和分歧处理 |

这些信号可以互相纠正，却不能简单相加成一个“总质量分”。例如，线上错误率下降但用户频繁重新生成文件，可能说明监测漏掉了内容错误；此时应抽查产物，并把确认的失败补进离线任务。

在工具选择上，我会先写清需要存哪些证据、怎样重跑一次尝试、谁来处理争议，再决定是否引入平台。无论使用什么框架，原始产物、运行记录和评分版本最好能导出；否则以后复查一条历史分数时，可能只剩面板上的数字。
