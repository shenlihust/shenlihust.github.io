写 AI 应用时，我们很容易把模型调用看成一个 HTTP 请求：组装 `messages`，发出去，等待流式返回，再把结果交给用户或工具。

直到应用接入更多用户、上下文变长、Agent 开始连续调用工具，问题才逐渐显现：为什么请求迟迟没有输出？为什么开始输出后又断断续续？为什么模型权重明明装得下，一提高并发就开始排队？为什么更换模型部署方式之后，工具调用也变得不稳定？

这些问题横跨应用、网关和模型服务。理解推理框架，能让我们知道每一层在做什么，把“模型慢”拆成可以调查的问题。

本文从一个故障排查 Agent 的模型请求出发，沿着它进入推理服务、参与调度、执行计算和返回结果的过程，解释应用工程师需要掌握的概念，以及这些概念会怎样影响应用设计。

> **来源与边界**：写作受到阿里云《AI Agent Handbook》中[《深入浅出推理框架》](https://aliyun.github.io/ai-agent-handbook/optimization/chapter-17/inference.html)启发，该页面未标注具名作者及明确发布日期。本文另外核对了推理框架官方文档和研究论文，资料查阅日期为 **2026 年 10 月 26 日**。案例、配图和实验方案为原创教学设计，没有进行 GPU 性能实测；框架能力应以实际使用版本为准。本文主要讨论自回归 Transformer 文本推理，不将其计算和缓存结论直接推广到所有模型架构。

## 先把位置放对：推理框架到底负责什么

训练让模型获得参数；推理使用这些参数，根据输入计算输出。这里的“推理”指 inference，既包含普通文本生成，也包含模型的 reasoning 过程，二者不能简单画等号。

一次模型调用背后，至少有几种不同的职责：

| 层次 | 主要负责什么 | 应用工程师通常怎样接触它 |
| --- | --- | --- |
| 应用 / Agent Harness | 组织上下文、选择工具、推进任务、管理状态 | 日常开发的主体 |
| 网关与服务接入 | 鉴权、限流、请求路由、协议与流式转发 | 调用 API，处理超时和错误 |
| 推理引擎 | 请求调度、KV Cache 管理、模型执行与采样 | 自部署、压测，或间接使用 |
| 计算运行时与硬件 | 执行算子，提供计算、显存与通信资源 | 选机型、做容量规划 |

“推理引擎”和“推理框架”没有绝对统一的命名边界。本文用推理引擎指核心执行系统，用推理框架指包含引擎及相关服务能力的软件；部署后再加上网关、监控、扩缩容等，才构成完整推理服务。这是便于讨论的划分，实际产品可能跨越多层。

只调用云端 API 的团队也会受这一层影响，只是没有直接操作调度器和 GPU 的权限。此时能做的事情包括设计请求、选择服务、观测耗时、控制并发，以及向服务提供方提出有证据的问题。

## 第一站：messages 如何变成模型的输入

假设用户问故障排查 Agent：“支付接口最近十分钟为什么变慢？”应用会把系统指令、工具定义、已有对话和当前问题组合起来。下面只摘出一个教学请求的关键字段，不对应某个服务的完整配置：

```json
{
  "model": "your-served-model",
  "messages": [
    {"role": "system", "content": "你是运维助手。分析需引用查询到的证据。"},
    {"role": "user", "content": "支付接口最近十分钟为什么变慢？"}
  ],
  "stream": true
}
```

模型不会直接理解 HTTP 或 JSON 中的 `role`。服务会应用 **Chat Template（对话模板）**，把各条消息转换为模型训练时约定的序列，再交给 **Tokenizer（分词器）** 编码成 Token ID。工具定义的具体拼接方式也取决于模型模板。

**Token 是模型处理序列的单位，不等于一个汉字、单词或屏幕字符。** 同一句话在不同分词器下长度可能不同，控制标记和工具描述也会占用上下文。因此，容量规划和计费分析应使用目标模型的 Token 口径。

Hugging Face 的[对话模板文档](https://huggingface.co/docs/transformers/main/en/chat_templating)特别强调：聊天消息最终仍是带有角色和控制标记的 Token 序列。即使底层模型相同，模板不匹配也可能影响效果。**兼容 API 格式，只能证明请求能够接入，不能证明模板、工具调用和思考内容的处理完全一致。**

_图 1：本文原创逻辑示意。接入、调度和执行可能属于同一服务，也可能分布在多个进程或节点；图中不限定部署拓扑。_

请求进入引擎后，还要等待调度。收到 HTTP 响应头，甚至收到第一个空的流式事件，都不能证明模型已经生成了正文。这个区别会直接影响后面的指标定义。

## 第二站：Prefill 与 Decode，同一次请求中的两种计算

理解大模型推理，最有用的起点是将输入处理和逐步生成分开。

### Prefill：处理已经知道的输入

**Prefill（预填充）**处理输入序列，建立后续生成需要的中间状态。因为输入 Token 都已经知道，标准因果 Transformer 可以在保持因果掩码的条件下，并行计算多个输入位置。

“并行处理输入”不表示 Token 互相独立，也不表示任意长输入都能瞬间完成。输入越长，计算、注意力访问和缓存空间的压力通常越大；服务也可能把 Prefill 拆成多个块处理。

从计算过程看，Prefill 最后得到的预测分布可以用来采样第一个输出 Token；从监控口径看，服务可能另行划分首次生成阶段。因此，应先确认指标边界，再比较数字。

### Decode：根据已有内容生成后续 Token

**Decode（解码）**沿着已生成序列继续计算。普通自回归生成中，下一个 Token 依赖前一步的选择，所以一个请求不能像处理已知输入那样，把任意多个未知输出位置直接并行算完。

![原创两阶段计算图：已知输入位置在 Prefill 中并行处理，随后 Decode 按依赖关系逐步生成输出，并复用历史 KV](/assets/img/posts/llm-inference-frameworks/prefill-decode.png)
_图 2：本文原创。每个小块代表一个抽象 Token 位置，不对应实际中文分词结果；普通自回归路径不包含投机解码。_

常见的经验是：**较长输入的 Prefill 更容易受计算能力限制，小批量 Decode 更容易受显存带宽限制。** Decode 每一步需要访问模型权重和历史 KV，单个请求新增的计算量却较少。

这里必须保留条件。批次大小、上下文长度、注意力结构、量化、并行策略和通信都会改变瓶颈。不能把“Prefill 吃算力，Decode 吃带宽”当作不需要分析的硬件定律。vLLM 的[优化文档](https://docs.vllm.ai/en/latest/configuration/optimization/)正是利用两类负载的差异讨论混合调度与调优。

这也帮助理解输入和输出的成本差异，但 **API 价格由供应商定价决定**，还受到硬件、批处理效率、缓存、商业策略等因素影响，不能从两阶段原理推导出固定价差。

## 第三站：KV Cache，为什么长上下文会挤占并发

### 缓存的到底是什么

注意力机制会为各位置计算 Query、Key 和 Value。生成新 Token 时，它的 Query 需要与历史位置的 Key、Value 交互。

可以粗略把 Query 理解为“当前在寻找什么”，Key 是参与匹配的线索，Value 是随后聚合的信息；三者实际上都是向量。模型有多层，每层又可能有多个注意力头，因此这些状态的空间会逐层、逐头累积。

**KV Cache 保存的是各层历史位置的 Key 和 Value 等中间状态。** 新一步可以复用它们，而不必重新计算整个历史序列。它既不是模型权重，也不是“上一个问题的完整答案”。[Hugging Face 缓存原理](https://huggingface.co/docs/transformers/main/en/cache_explanation)给出了相应的注意力计算说明。

复用也不意味着历史内容不再产生开销。对于全注意力模型，生成新 Token 时仍需读取和处理历史 KV；上下文增长后，即使命中了已有前缀，也可能影响后续 Decode。

### 显存要同时付几笔账

可以把推理显存粗略拆成：模型权重、KV Cache、激活与临时工作区，以及运行时额外开销。权重装得下，仅说明其中一笔账可能付得起。

对采用全注意力、各层 KV 形状一致的常见 Transformer，一个未考虑分片、量化元数据和分页浪费的估算式是：

```text
KV 字节数 ≈ 2 × 层数 × KV 头数 × 每头维度
             × 每个元素的字节数 × 所有活跃序列的缓存 Token 总数
```

其中 `2` 表示 Key 与 Value。GQA / MQA 使用的 KV 头数可能小于 Query 头数，不能直接拿 Query 头数代入。滑动窗口、MLA、混合注意力及其他状态结构需要另算。

举一个**纯算术教学例子**：32 层、8 个 KV 头、每头 128 维、每个元素 2 字节，那么每个缓存 Token 约占 128 KiB。单条 8192 Token 序列约占 1 GiB；16 条独立序列就是约 16 GiB，还没算后续输出增长和其他开销。这组数不指代某个实测模型，也没有扣除前缀共享可能节省的空间。

### PagedAttention：按需分配，而非整段预留

请求的最终长度事先未知。如果为每条请求准备一大块连续空间，容易产生预留浪费和碎片。PagedAttention 借鉴虚拟内存分页思想，用逻辑块映射到可不连续的物理 KV 块，按需要分配，并支持受控共享。[PagedAttention 论文](https://arxiv.org/abs/2309.06180)讨论了这一设计。

![原创 KV 分页图：两条请求的逻辑缓存块通过块表映射到不连续物理块，共同前缀可以共享同一个块](/assets/img/posts/llm-inference-frameworks/kv-cache-pages.png)
_图 3：本文原创概念图。省略层与设备维度；前缀共享需要引擎支持及匹配条件，末块仍可能存在未用空间。_

分页主要解决“怎样管理缓存空间”。**FlashAttention**主要通过分块计算等方式减少注意力运算中的显存读写；**Prefix Caching**主要解决跨请求复用。三者可以配合，不能当成同一种优化。[FlashAttention 论文](https://arxiv.org/abs/2205.14135)关注的是注意力计算的 IO 效率。

## 第四站：调度器为什么不能只按先来后到

一个在线模型服务同时面对长短不同的输入、输出，以及不断到达的新请求。调度器既要安排计算，也要判断 KV 空间是否足够。

### 连续批处理：每一步都能换乘客

Batching 把多个请求组合起来执行，摊薄权重访问等成本。传统的固定批次可能要等待批内长请求结束，才能接纳下一批；**Continuous Batching（连续批处理）**允许在迭代边界移出已完成请求，再补入新请求。

Orca 的核心贡献之一就是这种迭代级调度思想，详见 [OSDI 2022 论文入口](https://www.usenix.org/conference/osdi22/presentation/yu)。现代实现的准入、Prefill 和缓存管理更复杂，不能把概念图当作任何引擎的逐步运行日志。

![原创连续批处理图：固定批次中短请求完成后槽位空闲，连续批处理中新请求 C 在迭代边界加入](/assets/img/posts/llm-inference-frameworks/continuous-batching.png)
_图 4：本文原创调度示意。横轴为迭代，不代表固定毫秒；为突出槽位复用，省略新请求 Prefill、显存准入和不同迭代的耗时差异。_

对应用开发的含义是：单请求最快的配置，未必在多用户条件下最好；提高客户端并发，也不会让服务容量无限增长。超过承载能力之后，通常先看到队列和尾延迟增长。

### Chunked Prefill：别让长输入长时间挡住生成

一个新请求带来大量输入时，长 Prefill 可能干扰其他请求正在进行的 Decode。**Chunked Prefill（分块预填充）**把输入处理拆小，让调度器更细地安排 Prefill 与 Decode。

这依然有取舍：一次分给 Prefill 的预算增加，可能更快推进新请求；优先保护 Decode，则可能让已有用户输出更流畅。具体效果要看服务版本和负载，不能照抄别人的参数后宣称“两种延迟一起最优”。

KV 空间不足时还可能触发抢占与重算。比如查阅时的 vLLM V1 文档说明默认抢占模式为 `RECOMPUTE`；这与某些旧资料强调的换出到 CPU 内存不同。排查时应核对实际版本、等待队列和抢占指标。[来源：vLLM 调优与抢占说明](https://docs.vllm.ai/en/latest/configuration/optimization/)

## 第五站：前缀缓存，应用代码能影响的推理优化

Agent 调用日志工具后，还会将已有消息、工具调用和结果交给模型。相邻请求的开头经常重复，因此可以尝试复用已经计算过的前缀 KV。

**Prefix Caching（前缀缓存）**的关键是前缀匹配。一般不能只因为两段文字“语义相近”，就复用它们的注意力状态。SGLang 的 RadixAttention 使用树结构管理前缀复用，是这一方向的代表性设计。[来源：SGLang 论文](https://arxiv.org/abs/2312.07104)

应用可以提高可复用的机会：让系统指令和工具定义保持稳定、避免无意义的序列化差异，将确实需要变化的数据放到合适的位置。

![原创前缀缓存图：稳定系统指令与工具定义形成公共开头，新增问题位于后缀；在开头插入变化时间会缩短可复用前缀](/assets/img/posts/llm-inference-frameworks/prefix-cache.png)
_图 5：本文原创。颜色区分潜在可复用前缀与新增计算；实际命中还取决于模板、缓存块边界、模型配置、路由和缓存是否仍然存在。_

这里有三个容易混淆的边界。

第一，**缓存 KV 不等于缓存答案**。复用前缀后，模型仍然针对本次输入继续生成；应用层的结果缓存则可能直接返回已有回答。

第二，**命中主要减少 Prefill 工作**。vLLM 的[自动前缀缓存文档](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)明确指出，它不减少生成新 Token 的 Decode 时间。因此，“缓存命中很多”和“整次任务快了很多”之间还隔着实际耗时占比。

第三，**请求相似不保证命中**。缓存可能被驱逐，请求可能被路由到没有对应缓存的实例，服务也可能使用不同的隔离策略。动态时间放在开头，通常会缩短公共前缀，但不能笼统说一定让服务中的所有缓存失效。

上下文顺序首先要保持语义和指令层级正确。不要为了缓存，把本应作为不可信数据的工具输出提升成系统指令；也不要只为保持前缀而无限保留无关历史。缓存节省计算，不能替代上下文治理。

## 第六站：计算完成之后，输出还需要变成可用结果

### 采样与可复现性

模型计算得到下一个 Token 的分数，采样策略据此选择输出。`temperature`、`top_p` 等控制选择方式。低温度有助于降低随机性，却不能单凭一个参数保证跨版本、跨硬件、跨批次逐字一致。

服务如果提供确定性模式，还应核对它的适用后端与性能代价。[SGLang 的确定性推理文档](https://docs.sglang.io/docs/advanced_features/deterministic_inference)解释了批次变化与浮点归约顺序的关系。应用验收则要区分“文本完全相同”和“业务结果一致”：两次回答措辞不同，可以同样正确；两次都输出合法 JSON，也可以同样选错工具。

### 结构化输出：约束形式，仍要验证含义

推理框架可以根据 JSON Schema、正则表达式或语法规则限制合法的后续 Token，使输出满足支持范围内的格式约束。SGLang 的[结构化输出文档](https://docs.sglang.io/docs/advanced_features/structured_outputs)说明了这些入口。

但格式约束不会自动验证“服务名是否存在”“查询时间是否合理”“用户是否有操作权限”。输出还可能因长度限制、中断或拒绝等原因无法成为完整业务结果。因此应用仍要检查结束状态、解析参数、校验业务规则，并在工具执行处实施权限控制。

工具调用还涉及模型模板和输出解析器。迁移服务时，应覆盖普通回答、单次与多次工具调用、流式参数拼接、错误结束等路径。

### 投机解码：改变执行方式，尝试减少等待

**Speculative Decoding（投机解码）**先用便宜的方式提出多个候选，再让目标模型验证，接受可用的部分。采用正确的验证与采样算法时，可以保持目标分布；这并不等价于在任何工程配置下逐字复现某次普通采样。

它的收益取决于候选接受率、额外计算和服务负载，不能保证所有请求都变快。[经典投机解码论文](https://arxiv.org/abs/2211.17192)提供了算法依据，论文中的加速倍数不能直接作为自己服务的承诺。

最后，引擎输出的 Token 还需反分词、解析成正文或工具调用，再通过协议流式返回。用户看到的每一个文本块，也未必刚好对应一个 Token。

## 怎样衡量：先对齐延迟和吞吐的口径

讨论“快”之前，先选一个观测位置。本文将客户端请求发出记为 `t0`，首个含有效生成内容的事件到达记为 `t1`，最后内容到达记为 `tN`，整个响应完成记为 `t_done`。

![原创延迟时间线：请求发出后经历网络与排队、输入处理，首个有效输出到达后进入持续生成，最终响应结束；首 Token 与首个可见正文可能不相同](/assets/img/posts/llm-inference-frameworks/latency-metrics.png)
_图 6：本文原创指标口径示意，区段长度无实测含义。实际分段可能交错；底层 Token、流事件和用户可见正文需要分别观测。_

| 指标 | 本文采用的含义 | 能帮助判断什么 |
| --- | --- | --- |
| TTFT | `t1 - t0`，首个有效生成内容的等待时间 | 开始生成前的综合等待 |
| ITL / TBT | 相邻输出 Token 的时间间隔及其分布 | 生成是否有停顿 |
| TPOT | 请求级平均输出 Token 时间，常用 `(tN - t1) / (N - 1)` | 首 Token 之后的平均生成速度，`N > 1` |
| E2E latency | `t_done - t0` | 一次请求何时真正结束 |
| Throughput | 同一观测窗口内完成的请求数或处理的 Token 数除以时间 | 系统总体处理能力 |
| Goodput | 满足约定 SLO 的有效请求处理速率 | 处理量是否同时满足体验要求 |

TPOT 的 `N` 应与时间范围对应；不足两个 Token 时不能使用这个公式。SLO 是约定的服务目标，比如首 Token 和完成延迟的上限。Goodput 还需要说明失败请求、输出质量、计数窗口如何处理。

上述概念可对照 [NVIDIA 推理指标文档](https://docs.nvidia.com/nim/benchmarking/llm/metrics)。不同工具的平均方式和起止点并不完全相同，比较前要核对。TTFT 可能包含网络、网关、排队、分词与 Prefill，**客户端无法仅靠一个总数精确拆出 GPU 计算时间**。

应用还有一个更贴近用户的指标：**首个可见正文时间**。推理模型可能先生成思考内容，工具调用也可能先返回参数；即使底层已有 Token，界面仍可能没有可展示的答案。

采集流式数据时也要避免伪精度。空事件不算首 Token；一次事件包含多个 Token 时，测到的是块到达间隔，无法还原块内的逐 Token 时间。若拿不到可靠的 Token 级计数和时间戳，就如实报告事件级延迟。

吞吐同样不能只写“每秒多少 Token”。要交代输入 / 输出、模型与精度、上下文分布、并发和到达速率，以及 P50 / P95 / P99 延迟。更大的批次可能提高总吞吐，同时让单个用户等待更久。Goodput 的意义就在于将延迟约束纳入容量目标。[来源：DistServe 论文](https://arxiv.org/abs/2401.09670)

## 从一张卡到一个集群：还会多出什么问题

### 并行和量化，分别改变哪笔账

模型放不下，或者单个实例容量不足时，会用到不同并行方式：

| 方法 | 如何划分工作 | 主要需要注意什么 |
| --- | --- | --- |
| TP：张量并行 | 将层内张量计算切到多设备 | 同步与通信成本 |
| PP：流水线并行 | 将不同模型层放到不同设备 | 阶段等待和流水线气泡 |
| DP：数据并行 | 多组副本处理不同请求 | 副本资源和请求路由 |
| EP：专家并行 | 分布 MoE 的专家 | Token 分发、负载不均与跨卡通信 |

MoE（混合专家）每次只激活部分专家参与计算，但不代表部署时只需为激活参数准备存储。专家权重如何放置、是否卸载、通信是否高效，都影响实际资源需求。上表是原理划分，实际系统常组合多种并行策略。[来源：vLLM 并行策略](https://docs.vllm.ai/en/latest/configuration/optimization/)

量化则降低权重、激活或 KV 的数值精度。它们是不同对象，权重变小不等于 KV 按相同比例变小；节省空间也不保证等比例提速。应在目标模型、硬件和业务数据上验证质量、支持算子与性能。[进一步阅读：SGLang 量化文档](https://docs.sglang.io/docs/advanced_features/quantization)

### PD 分离：计算拆开了，状态还得送过去

**Prefill / Decode Disaggregation（PD 分离）**让两阶段在不同资源池执行。这样可以分别调整资源和并行方式，也能减少长 Prefill 对 Decode 的直接干扰。

代价是 Prefill 产生的 KV 状态必须传给 Decode 一侧，还增加了路由、传输、配比和故障处理的复杂度。网络带宽不足、请求较短或流量较低时，收益未必覆盖额外成本。DistServe 将资源分配、两阶段 SLO 和通信放在一起优化，而非只做物理拆分。

![原创 PD 分离图：同实例内 Prefill 与 Decode 共享资源，对照分离部署中的两个资源池；KV 状态经过传输后才能继续生成](/assets/img/posts/llm-inference-frameworks/pd-disaggregation.png)
_图 7：本文原创架构示意。资源池中各自持有所需模型权重；PD 分离不是将模型前半层和后半层切开，后者属于流水线并行的范畴。_

集群还面临缓存路由的取舍：有缓存的实例可能队列很长，空闲实例却需要重新 Prefill。路由应综合计算复用与等待，不能永远追逐命中率。Dynamo 的[官方项目说明](https://github.com/ai-dynamo/dynamo)将 KV 感知路由、分离部署和多级缓存列为集群层能力。

### 认识框架，先识别它所在的层

下面这张表是阅读地图，不是性能排名，也不表示项目只能用于表中场景。

| 软件或项目 | 理解它时可以先关注什么 |
| --- | --- |
| [vLLM](https://docs.vllm.ai/en/latest/) | 模型服务引擎、调度、分页 KV、模型与硬件支持 |
| [SGLang](https://docs.sglang.io/) | 推理运行时、前缀复用、结构化生成等能力 |
| [TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM) | NVIDIA 平台的推理算子、运行时与并行优化 |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) | C/C++ 推理实现、多硬件后端与量化模型运行 |
| [Ollama](https://github.com/ollama/ollama) | 模型运行、管理和 API 使用体验 |
| [Dynamo](https://github.com/ai-dynamo/dynamo)、[llm-d](https://github.com/llm-d/llm-d) | 引擎之上的分布式服务、路由与集群编排 |

应用团队选型时，先验证“目标模型 × 具体版本 × 硬件后端 × 所需功能”的组合，再比较自己的负载。尤其要验证工具调用、结构化输出、量化和并行模式能否一起工作。只看星标或一个峰值吞吐，无法回答这些问题。

## 回到 Agent：用户等的是整个任务

故障排查 Agent 先查询日志，再读取指标，最后综合证据。模型调用之间还有工具执行、网络和应用处理。

对于严格串行的任务，可以近似写成：

```text
任务耗时 ≈ 各次模型调用 E2E 之和
           + 各次工具执行时间之和
           + 编排、网络与其他等待
```

并行任务则要看依赖图上的关键路径，不能将所有分支耗时直接相加。重试和失败恢复也应进入任务级统计。

![原创 Agent 耗时图：模型决策、日志查询、再次决策、指标查询与最终回答构成串行关键路径，每次模型等待都会累积](/assets/img/posts/llm-inference-frameworks/agent-critical-path.png)
_图 8：本文原创任务示例，块宽不表示实测耗时。模型请求中的队列、Prefill、Decode 等时间已经包含在该次模型 E2E 中，不再重复累加。_

从这个角度看，推理优化需要与应用设计配合：

- **少做无效调用。** 能由确定规则完成的路由，不必每次请模型判断；能一次查全的信息，也不必机械拆成多轮。
- **控制有效上下文。** 保存证据来源，裁剪重复日志与无关内容；摘要后检查是否丢失后续判断需要的信息。
- **给输出设业务预算。** 内部工具选择未必需要长篇说明，但不能为了短输出截断必要参数或推理过程。
- **让独立工作并行。** 同时设置并发上限，观察是否把本地串行等待转移成模型服务排队。
- **观测任务结果。** 同时看完成时间、成功率、调用次数和实际账单；某一步更快但引发更多重试，未必是收益。

我的判断是，应用工程师最值得掌握的是这种连接能力：看见产品现象，知道需要哪一层证据，再决定调整上下文、应用流程还是推理服务。

## 不用先搭 GPU 集群，也能做的四组验证

以下是**待实施的实验方案**。可以先在已有 API 上观察客户端结果，有自部署服务时再补充队列、缓存与 GPU 指标。

| 对照 | 固定条件与唯一主要变量 | 记录什么 | 结果能回答什么 |
| --- | --- | --- | --- |
| 前缀复用 | 相同语义与模型配置；动态字段放前 / 放后，分别做冷、热请求 | 实际缓存 Token、TTFT、账单 | 请求结构有没有改变可复用部分 |
| 上下文增长 | 相同任务与输出预算，增加无关历史 | 输入 Token、质量、TTFT、E2E | 历史保留的收益是否值得成本 |
| 并发增长 | 固定请求长度分布，逐步提高并发；另行记录到达速率 | 吞吐、P95 / P99、错误、排队 | 何时开始违反 SLO |
| 业务输出 | 同一业务目标，对比冗长自由文本与所需结构化结果 | 正确率、输出 Token、重试、任务完成时间 | 减少输出和解析返工是否改善任务 |

第一组移动动态字段时，还应确认没有改变指令优先级；冷缓存也不能仅凭“第一次请求”断定，共享服务可能已经有相同前缀。拿不到命中信息时，只能报告观察到的时延差异，不能认定原因。

每组都应包含重复采样，说明预热、测试时段、模型版本、参数、工具链版本、错误与超时处理。正式比较缓存策略时，避免前一组缓存污染后一组；比较并发时，注明使用闭环并发客户端还是固定到达速率，否则负载本身也可能被响应速度改变。

最小记录可以包含下面这些字段。这是观测设计，**不是某框架现成返回的标准 Schema**；缓存数量、服务端时间和请求费用拿不到时保留为空，不做猜测。

```text
task_id / request_id / model_revision / serving_version
input_tokens / output_tokens / cached_input_tokens
request_sent_at / first_content_at / first_visible_text_at / response_done_at
finish_reason / error_type / retry_count
tool_duration / task_success / billed_cost
```

这些记录能让问题变得具体：不是笼统地说“模型响应慢”，而是说“在固定长度分布下，并发升高后 P95 首内容延迟恶化，输出阶段变化较小，需要进一步查看队列和准入情况”。这仍是待验证的诊断方向，但已经知道下一步该找什么证据。
