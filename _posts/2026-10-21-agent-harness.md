一个 Agent 产品通常能连续调用工具、读写文件、记住任务进度、等待用户授权，甚至把子任务交给其他 Agent。这些能力由谁提供？模型接口、工具、上下文、沙箱和任务调度，又是怎样连接起来的？

这些问题指向同一层系统：**Agent Harness，围绕模型构建、负责组织任务执行的运行系统。**

模型根据输入判断下一步；Harness 准备输入、接入模型、执行动作、保存状态，并把结果送回下一轮。理解它的架构，需要同时看清三个部分：核心执行回路、支持回路的各个模块，以及贯穿整个过程的状态和反馈。

本文先画出整体结构，再逐个拆解模块，最后串起一次任务的执行过程。讨论的是通用职责与设计方式，不是某个产品的源码说明；不同实现可以合并模块，也可以把其中一部分交给外部服务。

## 1. Harness 在 Agent 系统中的位置

理解 Harness，可以先把 Agent 系统分成三部分：

![用户请求进入 Harness，由它调用模型并执行文件读取；模型提供行动建议，环境提供实际内容。](/assets/img/posts/agent-harness/position-unified.png){: width="1536" height="1024" }
_用户请求进入 Harness，由它调用模型并执行文件读取；模型提供行动建议，环境提供实际内容。_

| 部分 | 负责什么 | 典型内容 |
| --- | --- | --- |
| 模型 | 理解输入，生成回答或下一步行动请求 | 推理、文本生成、工具选择 |
| Harness | 组织模型与环境之间的交互 | 执行循环、上下文、工具调度、状态、权限 |
| 外部环境 | 提供数据、计算资源与实际操作对象 | 文件系统、浏览器、数据库、业务 API |

用户界面位于入口侧。它把用户输入交给 Harness，再展示文本、工具进度和待确认事项。模型服务与工具环境则位于调用侧：Harness 调用前者获取决策，通过后者产生实际效果。

这里有一个重要边界：**模型生成工具调用请求，工具执行器才真正执行操作。** 模型说要读取文件，不代表它已经读到了文件；模型说任务完成，也不等于外部环境已经达到目标状态。

LangChain 在 [The Anatomy of an Agent Harness](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness) 中采用宽泛定义，把模型之外的代码、配置和执行逻辑都放进 Harness 的范围。本文采用这一视角，但在讲解时把内部执行模块和外部工作环境分开，便于看清接口。

### 运行系统与工作环境，是两个观察角度

围绕 Harness 的设计和改进，称为 **Harness engineering**。相关博客常从两个角度讨论它：

- **构建 Agent 的人**关心循环、模型适配、工具、上下文、权限和恢复机制。
- **使用 Agent 的人**关心项目规则、知识文档、Skills、测试与检查工具，让已有 Agent 更好地适应具体工作。

Birgitta Böckeler 在 [Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html) 中区分了产品内置的 Harness 与用户在其外侧搭建的 Harness。OpenAI 的 [Harness engineering](https://openai.com/index/harness-engineering/) 则重点讨论仓库知识、可检查的架构约束和反馈环境。

本文主要展开第一种视角。项目规则和测试环境会在上下文、扩展与反馈模块中找到位置。

### 从一次读取请求看三方分工

假设用户问“这个项目怎样启动”。模型可以根据当前信息提出读取 README 的请求，但文件路径是否有效、是否允许读取、文件内容如何返回，都由 Harness 处理。读到的文档进入下一轮上下文后，模型才能据此说明启动命令。

如果文档提到还需要环境配置，模型可以继续请求相关文件。这里多出来的能力，是运行系统把“提出问题—取得资料—继续判断”连接成了可重复执行的过程。示例只是帮助区分三方职责，不要求每个任务都采用相同路径。

## 2. 整体架构：以执行循环为中心

Harness 可以按职责拆成七个模块。这一划分参考 Barbaste 等人的 [Harness Engineering 源码研究](https://arxiv.org/abs/2609.00006)，用于组织讲解，不代表所有实现都必须有七个独立组件。

![Harness 架构：上下文、执行循环、模型接入与工具构成主流程，权限检查约束执行，工具结果回流至上下文；编排、扩展和持久化提供支持](/assets/img/posts/agent-harness/architecture.png){: width="1536" height="1024" }
_依据本文职责划分原创设计，使用 GPT 生图并校正连线。模型与执行环境位于运行控制系统之外；箭头展示主要交互，非固定部署拓扑。编号对应下表七项职责，权限与沙箱共同构成第⑤项。_

| 模块 | 核心职责 | 主要连接对象 |
| --- | --- | --- |
| Agent 循环 | 驱动一轮轮决策，管理继续、等待与停止 | 上下文、模型、工具、任务状态 |
| 模型接入 | 适配请求、响应与能力差异 | 模型服务、执行循环 |
| 工具与动作 | 把行动请求变成可执行操作和结果 | 权限策略、执行环境、外部服务 |
| 上下文与记忆 | 组织当前输入，保存和检索需要延续的信息 | 历史记录、文件、检索服务、模型接入 |
| 权限与沙箱 | 判断动作是否允许，限制资源访问范围 | 工具执行器、身份系统、隔离环境 |
| 任务编排 | 管理任务分解、依赖、委派和汇总 | 一个或多个 Agent 循环 |
| 扩展机制 | 接入工作方法、工具和生命周期逻辑 | 上下文、工具注册表、执行循环 |

这七项之外，还有贯穿全程的能力：**会话与状态持久化、事件记录与可观测性、结果验证与系统评估。** 它们可能被实现成独立服务，也可能嵌在循环、存储层或中间件里。

读图时可以抓住两条线：

**执行线：上下文 → 模型 → 行动请求 → 权限检查 → 工具执行 → 结果回流。**

**状态线：每一步产生的消息、请求、结果和进度，都需要关联到同一个任务，并按恢复需求保存。**

执行线解释系统怎样向前推进，状态线解释系统怎样知道自己走到了哪里。

### 模块之间实际交换什么

这些模块通过明确的数据对象协作。可以把一次运行中最重要的对象理解为下面几类，名称只是教学示意：

| 对象 | 关键内容 | 谁使用它 |
| --- | --- | --- |
| 任务状态 | 目标、当前阶段、未完成项、预算 | 循环与编排 |
| 模型输入 | 消息、相关材料、可用工具定义 | 模型接入层 |
| 行动请求 | 工具名、参数、调用 ID | 权限模块与执行器 |
| 执行结果 | 调用 ID、状态、内容或产物引用 | 历史记录与上下文模块 |
| 运行事件 | 时间、任务 ID、操作类型、结果 | 界面、持久化与观测 |

调用 ID 把请求和结果对应起来，任务 ID 把多轮调用归到同一次工作。没有这层关联，两个同时执行的工具即使都返回正确内容，也可能被错误地放进对方的上下文。架构图中的箭头，实际传递的就是这些有结构、有归属的数据。

## 3. Agent 循环：控制任务怎样继续

Agent 循环是 Harness 的控制中心。它协调其他模块，让一次模型调用接上下一次调用。

![工具返回、用户回复和验证反馈驱动下一轮；取消和预算属于运行控制。图中省略工具执行前的权限细节。](/assets/img/posts/agent-harness/loop-unified.png){: width="1536" height="1024" }
_工具返回、用户回复和验证反馈驱动下一轮；取消和预算属于运行控制。图中省略工具执行前的权限细节。_

最基本的一轮包含四个阶段：准备上下文，调用模型，处理响应，再把执行结果纳入后续输入。模型请求工具时进入执行分支；需要用户补充信息时进入等待分支；满足结束条件时退出。

这里的循环不只是一个不断调用 API 的 `while`。一旦存在流式响应、长时间工具执行和人工审批，它就需要表达明确的运行状态。

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| 运行中 | 正在调用模型或处理动作 | 接收结果，推进下一步 |
| 等待工具 | 外部操作尚未结束 | 等待完成事件或查询执行状态 |
| 等待用户 | 缺少信息或需要授权 | 保存待处理事项，收到答复后恢复 |
| 已完成 | 达到任务约定的结束条件 | 保存结果并交付 |
| 受阻或失败 | 无法继续，或执行发生不可恢复错误 | 保留原因和已有进展 |
| 已取消或预算耗尽 | 被外部控制条件停止 | 取消可取消的工作，记录剩余事项 |

这是职责示意，具体状态名由实现决定。重要的是区分“模型这一轮输出结束”和“整个任务完成”：前者只是一次推理的边界，后者需要结合任务目标判断。

循环还管理运行边界，例如最大轮数、截止时间、取消信号和重试次数。模型可以建议下一步，但这些约束应由运行时实际执行。否则，一个持续请求同样失败操作的模型，会让系统无休止地消耗资源。

用户在执行过程中补充要求，也需要经过循环协调。系统要决定何时把新消息纳入上下文，是否中断当前操作，以及哪些正在执行的动作已经无法撤回。入口侧的消息队列与运行侧的取消机制，因此也是循环设计的一部分。

### 工具还没结束时，循环做什么

例如模型发起一条耗时较长的检查命令，执行器先返回“已启动”和任务 ID。循环应保存这个 ID，进入等待工具状态；后续收到退出码和完整结果，再决定下一步。它不应把“启动成功”解释成“检查通过”。

如果此时用户补充“只检查，不修改”，新约束应进入后续上下文和权限判断。取消请求则需要传给支持取消的执行器；不能取消或已经完成的外部动作，也要如实记录。循环管理的是任务生命周期，而不只是模型消息列表。

## 4. 模型接入：把模型能力变成稳定接口

模型接入模块位于执行循环与模型服务之间。它负责两个方向的转换：把系统内部的上下文和工具定义转换成模型请求，再把响应转换成运行时能够处理的事件。

![请求方向适配消息和能力，响应方向组装事件；模型本轮结束不等于任务完成。](/assets/img/posts/agent-harness/adapter-unified.png){: width="1536" height="1024" }
_请求方向适配消息和能力，响应方向组装事件；模型本轮结束不等于任务完成。_


这个模块通常包含三类工作。

**请求构造。** 整理消息角色、文本和图片等内容，转换工具参数描述，配置输出限制与模型支持的选项。上游上下文模块决定“哪些信息值得提供”，适配层负责“怎样按服务协议发送”。

**响应解析。** 区分普通文本、工具请求、结束原因和错误。流式调用还需要组装增量事件：尚未接收完整的工具参数，通常不能直接交给执行器运行。每个工具请求与返回结果也必须保留可关联的标识。

**能力与故障管理。** 维护模型是否支持特定输入形式、工具调用方式和参数；处理限流、网络异常与服务错误。有些能力可以通过适配统一，有些需要明确保留差异，不能靠改字段名假装等价。

模型路由也可以放在这一层，或由上层编排决定。例如，不同子任务使用不同模型。路由决策需要结合质量、延迟和总任务成本，不能只比较单次请求价格。

统一接口的价值是缩小协议差异对其他模块的影响。它不会消除模型行为差异：更换模型后，工具选择、参数生成和结束判断仍需要重新评估。

### 一条工具请求如何经过适配层

运行时内部可以用下面的对象表达工具请求，字段为教学示意：

```json
{
  "type": "tool_request",
  "call_id": "call_17",
  "name": "read_file",
  "arguments": {"path": "README.md"}
}
```

模型服务可能分多次发送工具名称和参数片段。适配层先按调用标识聚合，收到完整参数后再解析；如果连接中断，不能把半段 JSON 当成有效动作。完整请求交给循环后，还要经过工具参数校验和权限检查。

工具完成时，结果沿同一个调用 ID 返回。下一次模型请求必须按目标服务的协议保留这组对应关系，否则模型可能无法判断哪条请求成功、哪条仍未结束。适配层统一的是协议表达，工具执行器仍负责操作的业务语义。

## 5. 工具与动作：连接真实环境

工具模块为模型提供可执行能力。读取文件、检索资料、运行命令、操作浏览器和调用业务 API，都可以通过这一层接入。

![读取文件展示请求到结果的路径；长命令和不同失败类型有各自处理方式。字段为教学示例。](/assets/img/posts/agent-harness/tools-unified.png){: width="1536" height="1024" }
_读取文件展示请求到结果的路径；长命令和不同失败类型有各自处理方式。字段为教学示例。_

一个工具有两种面向不同对象的接口：

| 接口 | 面向谁 | 包含什么 |
| --- | --- | --- |
| 工具描述 | 模型 | 名称、用途、输入参数、适用条件 |
| 执行实现 | 运行时 | 参数校验、调用代码、超时与取消、结果和错误处理 |

模型看到的是能力说明，执行器持有的是实际实现。工具注册表把两者关联起来；某一轮暴露给模型的工具列表，可以只是注册表中符合当前任务和权限的一部分。

典型调用路径是：

`工具请求 → 查找工具 → 校验参数 → 检查权限 → 执行 → 整理结果 → 回传循环`

这里的结果需要足够明确。成功、失败、部分完成和结果未知，对下一轮决策的含义不同。长输出可以保存为产物，再返回摘要和可读取的位置；不能因为截断了日志，就把关键错误一起丢掉。

### 执行环境也是工具设计的一部分

工具实现可能直接运行在应用进程里，也可能调用独立进程、容器、远程沙箱或外部服务。不同方式影响隔离、延迟和生命周期管理。

尤其是长时间命令，调用返回不一定意味着进程结束。执行器可以先返回任务标识，再提供等待、查询输出与取消能力。循环需要知道它收到的是“已启动”还是“已完成”。

重试同样属于执行契约。读取操作和有副作用的写操作不能一概处理：外部写入成功但响应丢失时，再调用一次可能重复执行。服务支持幂等键时可以利用它；否则需要查询状态，或明确保留“结果未知”。

MCP 是这一层的一种接入方式。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)定义了应用与服务之间交换工具、资源和提示模板的协议。工具也可以由本地函数或普通 API 提供；无论采用哪种连接方式，调用策略与结果处理仍要由应用组织。

### 好的返回值让下一步有依据

以读取 README 为例，下面几种结果需要被明确区分：

| 实际情况 | 应返回的信息 | 后续动作 |
| --- | --- | --- |
| 文件读到 | 成功状态、内容、实际路径 | 根据内容继续分析 |
| 路径不存在 | 不存在的路径、错误类型 | 检索目录或调整路径 |
| 无权访问 | 被拒绝的资源和原因 | 调整范围或等待授权 |
| 内容过长 | 截断说明、总量或剩余读取方式 | 按需继续读取 |
| 执行超时 | 超时状态、是否仍在运行 | 查询进程或安全终止 |

工具描述也要说明限制。例如编辑工具可以要求目标片段唯一，或检查读取后文件是否变化。这样的前置条件能保护其他写入者的修改，并给模型明确的重新读取信号。

## 6. 上下文与记忆：决定模型这一轮知道什么

上下文模块负责构造每次推理的输入。它要从用户要求、系统规则、工具说明、历史消息、检索结果和工作产物中，选择当前需要的信息。

![当前材料与会话状态进入上下文组装，长期记忆按需检索后进入本轮输入；新经验经过筛选与确认再写入跨任务记忆](/assets/img/posts/agent-harness/context-memory.png){: width="1536" height="1024" }
_会话与任务状态支持当前任务连续执行，长期记忆保存跨任务可复用的信息。两者都需要经过加载或检索才能进入本轮上下文；新经验经过筛选与确认才写入长期记忆，并支持更新、纠正与失效。_

这项工作可以拆成四步：

1. **收集**：取得任务目标、会话历史、项目规则和相关外部资料。
2. **选择**：判断哪些内容与当前步骤相关，哪些已经过期或重复。
3. **组织**：保留来源、优先级和结构，让指令、外部材料与工具反馈可区分。
4. **控制容量**：为模型输出预留空间，对长历史做摘要，对大产物按需读取。

Prompt 是其中的指令部分。上下文工程处理的是整个输入集合，以及它在多轮执行中怎样变化。

### 当前上下文、任务状态和长期记忆

这几个概念容易混用，按用途区分更清楚：

| 信息 | 用途 | 常见载体 |
| --- | --- | --- |
| 当前上下文 | 供这一次模型调用直接使用 | 组装后的消息与工具定义 |
| 会话历史 | 记录这段交互发生过什么 | 消息与工具事件记录 |
| 持久化任务状态 | 支持暂停、恢复和进度管理 | 检查点、任务表、进度文件 |
| 长期记忆 | 跨任务复用经过筛选的信息 | 用户偏好、项目知识、经验记录 |

持久化的信息不会自动进入模型上下文。它需要经过加载、检索和筛选，才能成为这一轮的输入。反过来，某条内容进入过上下文，也不意味着它已被可靠保存。

压缩和外部存储解决的问题也不同。压缩把历史缩成更短的表达，可能丢失细节；外部存储保留原始材料，但需要再次读取。常见组合是保存原始产物，在上下文里保留摘要、关键结论和可定位的引用。

长期记忆还需要写入规则。一次任务中的临时判断，不宜直接成为永久规则；可以复用的信息应有来源、适用范围和更新时间，并能纠正或失效。记忆系统的重点是信息怎样进入、检索和更新，存储选用文件、数据库还是检索服务，则取决于具体需求。

### 长日志怎样进入有限的上下文

假设一次检查产生了很长的日志。把所有内容直接送给模型，可能挤掉任务要求和关键代码。上下文模块可以保留错误位置、失败摘要、退出码以及完整日志的存储位置；下一轮如果需要某段细节，再通过工具读取。

这里的筛选不能只按“越新越重要”。用户要求、权限边界、未完成项往往需要持续保留；已经失效的推断则应被更新。压缩摘要还应区分“已验证结论”和“待确认假设”，避免把一次猜测保存成确定事实。

一个实用的任务摘要至少包含：目标、当前进展、证据位置、未完成项和下一步。文件位置或版本也应保留，方便恢复时核对，而不是只留下“基本完成”这样的描述。

## 7. 权限与沙箱：动作授权和资源隔离

权限与沙箱共同约束工具执行，但它们回答不同的问题。

![左侧决定动作是否允许，右侧限制执行资源。目录和网络限制是示意配置。](/assets/img/posts/agent-harness/permissions-unified.png){: width="1536" height="1024" }
_左侧决定动作是否允许，右侧限制执行资源。目录和网络限制是示意配置。_

**权限策略回答：当前用户和任务是否允许执行这个动作？** 它可以结合身份、资源范围、操作类型与已有授权，决定放行、拒绝或等待人工确认。

**沙箱回答：执行进程实际能够接触哪些资源？** 它通过文件系统访问、网络连接、进程隔离和凭据配置等机制，限制动作的影响范围。


工具位于沙箱里，不代表每个操作都符合用户意图。只读任务中的写入，仍然应被权限策略拒绝。反过来，用户批准了某项操作，也不意味着执行进程应该获得整台主机的访问权限。

这一模块需要在执行路径上强制生效。提示词里的“不要访问其他目录”可以指导模型，但真正的访问限制必须落在执行器、操作系统或资源服务中。对远程业务系统，服务端还需要校验身份和资源权限。

审批则是一次可恢复的状态转换：保存具体待执行动作，向用户展示目标与影响，收到授权后再继续。授权应与实际执行的动作匹配；参数变化后不能直接套用旧批准。

### 同一个编辑请求，两层检查怎样配合

用户要求修改项目 README 时，权限模块先检查当前任务是否允许写入、目标是否属于授权目录。若策略要求确认，就保存具体文件与拟执行操作，等待用户答复；拒绝时则不进入执行器。

放行之后，工具仍在受限环境中运行：项目目录可以读写，个人目录不可见，网络连接按配置限制。即使命令参数有误，隔离机制也能缩小影响范围。

凭据也属于这条边界。调用远程服务时，应由可信的身份和凭据管理机制提供所需访问权限，而不是让模型通过填写“管理员”之类的参数自行获得身份。最终资源服务仍要执行自己的授权校验。

## 8. 任务编排：管理计划、依赖和多个执行单元

单个 Agent 循环管理一条连续执行过程。编排模块处理更大范围的工作结构：任务怎样分解，哪些步骤相互依赖，是否委派，以及结果怎样汇总。

![独立检查可以并行，汇总阶段核对证据。下方汇总与输出均属于主 Agent 的工作阶段。](/assets/img/posts/agent-harness/orchestration-unified.png){: width="1536" height="1024" }
_独立检查可以并行，汇总阶段核对证据。下方汇总与输出均属于主 Agent 的工作阶段。_

首先要区分**计划内容**与**调度状态**。模型生成的待办清单描述它打算怎样做；编排系统维护的任务状态，才决定哪些工作已经启动、完成、失败或被取消。清单上的一个勾，不应自动等同于实际执行成功。

编排可以有几种形态：

| 形态 | 控制方式 | 适合解决的问题 |
| --- | --- | --- |
| 单 Agent 推进 | 一个循环维护计划并逐步执行 | 上下文紧密关联、步骤依赖较强的任务 |
| 固定工作流 | 程序预先定义阶段与转移条件 | 路径明确、需要稳定控制的业务流程 |
| 主 Agent 委派 | 主 Agent 把工作交给子 Agent，再接收结果 | 可分离的探索、分析或检查 |
| 多角色协作 | 不同角色按约定交接和反馈 | 需要生成、审查、修订等不同职责的任务 |

引入子 Agent 后，每个执行单元可以有自己的上下文、工具集合和预算。这样能隔离局部信息，也可能并行推进独立工作；代价是增加交接、重复探索和结果整合成本。

一个完整的委派接口至少要说明目标、输入、允许访问的资源、输出要求和结束条件。调度器还要处理并发限制、超时、取消传播，以及多个 Agent 修改同一资源时的冲突。子 Agent 返回的总结需要能指向实际产物或证据，主 Agent 才有依据继续工作。

Anthropic 的 [Harness design for long-running application development](https://www.anthropic.com/research/harness-design-long-running-apps) 展示了规划、生成和评估三个角色的组合。它适合说明角色分工怎样形成反馈，但这是针对特定任务构造的架构，并非所有 Harness 都需要三个 Agent。

### 怎样把“评估升级影响”拆成可交接的工作

依赖兼容性、受影响接口和测试覆盖，可以分别只读分析，再交给主 Agent 汇总。每个子任务不仅要收到一句“帮我看看”，还应收到检查范围、禁止修改的约束，以及输出格式：发现、依据文件、风险和未确认项。

有依赖的步骤则不能随意并行。例如必须先确定目标版本，才能检查该版本的迁移要求。调度器可以把这个依赖记录在任务状态中，前置工作未结束时不启动后续步骤。

汇总也不是拼接三段文字。主 Agent 需要处理相互矛盾的结论，核对证据是否针对同一版本，并明确尚未完成的检查。一个子任务失败时，可以重试、缩小范围或保留受阻项；不能把其他两个成功当成整个任务完成。

## 9. 扩展机制：让能力接入现有运行过程

扩展模块提供稳定接入点，使新增工作方法、工具或策略能够进入已有执行过程。

![Skill、MCP、Hook 与 ACP 分别进入不同接口；MCP 的资源也可按需进入上下文。](/assets/img/posts/agent-harness/extensions-unified.png){: width="1536" height="1024" }
_Skill、MCP、Hook 与 ACP 分别进入不同接口；MCP 的资源也可按需进入上下文。_

这些扩展落在不同位置：

| 扩展形式 | 接入位置 | 作用 |
| --- | --- | --- |
| Skills | 上下文与资源加载 | 提供领域知识、操作步骤及配套材料 |
| 工具插件、MCP 服务 | 工具注册与执行 | 增加可调用的外部能力 |
| Hooks / Middleware | 生命周期节点 | 在调用前后执行检查、注入信息或记录事件 |
| 模型适配器 | 模型接入层 | 增加模型服务或能力支持 |

[Agent Skills](https://agentskills.io/home)以 `SKILL.md` 和可选的脚本、参考资料等资源封装工作方法。Harness 可以先发现名称与描述，匹配任务后再加载详细内容，减少无关指令占用上下文。Skill 中包含脚本时，执行脚本仍应经过工具和权限机制。

Hooks 和 Middleware 则把程序逻辑放到生命周期上，例如模型调用前补充环境信息、工具执行后记录结果、准备结束时检查必要步骤。具体能否修改、阻止或重试动作，由实现提供的接口决定。多个扩展同时生效时，还需要约定执行顺序和错误传播方式。


[ACP（Agent Client Protocol）](https://agentclientprotocol.com/get-started/introduction)面向编辑器等客户端与 Coding Agent 的通信，帮助入口侧发送任务、展示过程和处理交互。它与面向工具服务的 MCP 处在不同接口上，也不等于系统内部的子任务调度协议。

扩展机制的核心，是让每种能力进入正确的模块，并沿用已有的状态、权限与事件约定。把任意代码挂进循环，只解决了“能运行”，还没有解决“怎样与系统协作”。

### 一个能力如何通过不同扩展接入

以“按团队规范做代码审查”为例，Skill 可以说明审查顺序和关注点；代码检索工具提供读取能力；Hook 可以在工具返回后记录所查文件，或在结束前提醒检查遗漏。三者分别承载方法、动作与流程逻辑。

Skill 不会自动执行工具，MCP 接通也不会自动决定何时调用，Hook 的运行权限更不能由一段外部文档自行授予。运行系统需要保持这些边界，才能让扩展可组合、可诊断。

接入点还应处理失败：可选的记录 Hook 出错是否影响主任务，强制校验失败是否阻止执行，以及工具服务断开后是否撤下对应能力。这些行为应由扩展契约说明，避免核心循环依赖某个插件的隐含约定。

## 10. 贯穿各模块的状态、观测与评估

把前面七个模块接起来，可以形成执行回路。要支持长任务和持续维护，还需要从全局处理三类问题。

![检查点、Trace 和评估分别用于恢复、诊断与比较；恢复仍需核对外部状态。](/assets/img/posts/agent-harness/state-unified.png){: width="1536" height="1024" }
_检查点、Trace 和评估分别用于恢复、诊断与比较；恢复仍需核对外部状态。_

### 状态持久化：执行过程怎样恢复

会话历史保存交互，检查点保存可恢复状态，工作区保存实际产物。它们需要建立关联，否则可能出现“记录显示已完成，产物却不存在”的情况。

恢复时，不仅要加载历史，还要核对当前环境：文件是否变化，后台进程是否还在，外部操作是否已经成功。保存检查点无法自动消除“外部操作已执行、记录还没写入”的时间窗口，因此工具的操作标识和状态查询能力同样重要。

Anthropic 的 [Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) 用初始化、进度材料和增量工作维持跨会话连续性。它提供了一种具体实现；更一般的原则是，让下一次运行能够找到可信的任务状态与工作产物。

### 可观测性：能否还原一次执行

日志告诉我们发生过什么，Trace 把一次任务中的模型调用、工具调用与子任务串起来，指标则帮助比较多次运行。

有用的执行记录应能够回答：模型当时看到了哪些关键信息，为什么进入某个分支，工具实际返回什么，哪一步消耗了时间和预算。记录还需要关联任务、调用和产物，同时按需要脱敏，避免把凭据或无关敏感内容写入日志。

MongoDB 的 [Agentic Platform 架构文章](https://www.mongodb.com/company/blog/technical/designing-an-agentic-platform-infrastructure-that-makes-agents-work) 将可观测性与状态、权限、编排、记忆、评估一起讨论，并区分单个 Harness 与运行多个 Harness 的平台基础设施。这一划分有助于避免把部署、租户治理等平台问题都塞进一个循环。

### 验证与评估：当前任务和整套系统分别怎样判断

**任务内验证**检查这次产物是否满足要求，结果可以回到执行循环，驱动修订或交付。检查方式可以是测试、产物检查、模型评价或人工审阅，需要与任务的成功条件对应。

**系统评估**在一组任务上比较 Harness 的整体表现，包括成功率、成本、耗时、人工介入和恢复能力。修改上下文策略或工具接口后，单次演示变好，并不足以说明整体改进。

LangChain 的 [Improving Deep Agents with harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering) 展示了利用执行轨迹定位失败，再调整提示、工具和中间件的过程。它说明评估不只是上线前的一个检查点，也能为 Harness 的持续改进提供依据。

### 三份记录，解决三个不同问题

假设一次资料分析在中途断开。检查点记录“已读取哪些文件、仍缺什么”，用来恢复工作；Trace 记录各次调用的时间、输入引用与错误，用来判断为什么断开；评估记录则在多次任务之间比较新旧恢复策略是否有效。

这三份记录可以共享任务 ID，但用途不能相互替代。一份详尽日志未必包含直接可加载的恢复状态；一次验收通过，也不能说明其他任务上的效果更好。

系统评估可以固定一组代表性任务，让两个 Harness 版本使用相同模型与相近条件运行。除了最终是否完成，还应比较重复调用、超时、人工介入和成本。这样才能判断一次“更强的检查”究竟减少了失败，还是只增加了调用次数。

## 11. 一次任务怎样穿过这些模块

把模块放回运行过程，可以按下面的顺序理解：

![只读任务中，每轮新信息推动下一步；再次读取配置同样需要经过模型接入、权限与工具执行。](/assets/img/posts/agent-harness/journey-unified.png){: width="1536" height="1024" }
_只读任务中，每轮新信息推动下一步；再次读取配置同样需要经过模型接入、权限与工具执行。_

1. **入口接收任务。** 会话层关联用户、历史和工作区，建立本次运行状态。
2. **上下文模块准备输入。** 组合目标、规则、相关材料与当前可用的工具；必要时加载 Skill。
3. **循环通过模型接入层发起推理。** 适配器发送请求，接收并解析响应。
4. **循环处理行动请求。** 工具模块查找实现并校验参数；权限模块决定执行、拒绝或等待确认。
5. **执行器调用环境。** 操作在指定进程、沙箱或服务中发生，返回结果或后台任务标识。
6. **结果与状态回流。** 保存调用记录和产物引用，更新任务状态；上下文模块选择下一轮需要的信息。
7. **按需要进入编排分支。** 委派子任务、等待依赖或汇总结果，再回到主任务。
8. **处理结束条件。** 根据任务约定验证产物，记录完成、受阻、取消或预算耗尽等结果，并向用户反馈。

扩展逻辑可以挂在这些阶段，可观测性记录整个过程。遇到用户答复、工具完成或中断恢复时，系统会从相应状态继续，而非每次都从头执行。

真实工程中的模块不必与本文章节一一对应。例如，[Microsoft Agent Framework 的 Harness 文档](https://learn.microsoft.com/en-us/agent-framework/concepts/harness) 按 Chat client、Chat pipeline、Agent / Context providers、Middleware 和应用界面组合能力。同一种职责，可以由不同的软件抽象承载。

阅读一个具体 Harness 项目时，可以沿四个问题建立架构地图：**谁驱动循环，谁准备上下文，谁执行动作，谁保存并检查结果。** 再追踪权限、编排与扩展怎样接入这四条主线，就能理解它的主要结构。

### 把执行链路读成连续的信息变化

用“说明项目怎样启动”这个只读任务观察链路：开始时系统只有问题和项目入口；读取 README 后有了启动命令；发现环境变量说明缺失后，再读取配置文档；最后模型用两份来源组织回答。每一轮增加的是新证据，下一步因此发生变化。

如果文档没有给出必要信息，合理的结束可能是列出已知步骤和待确认项，而不是猜测配置。若用户只要求说明启动方式，读取资料后也不应自行启动服务。最终交付范围由任务目标和授权决定。
